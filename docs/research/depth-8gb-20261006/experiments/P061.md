## Question

For PrismML #330: with min-Q (2096db283) vs the old rule (8a6d2ea12), does file-rewrite decode go up below the
32768 cap, and is prefill unchanged at 30k and 60k?

## Why

Follow-up to P60, asked by the 4070 session for the #330 comment. Expectation (4070 session): "file-rewrite decode up
below the 32768 cap; prefill unchanged."

## Plan and gate

Notebook: "P61 (queue 06b, for PrismML #330): bin-tier (old rule, > 8 queries) vs bin-minq (>= 64), lookup on,
F16=32768. Fresh 30k and 60k prefill (quick_tps --depth 30000 / 60000, one server each) and lookup_ab.py at depth
30000. Expectation (4070 session): file-rewrite decode up below the 32768 cap; prefill unchanged. Post data on #330
(no commit)." No numeric gate.

## Method

Per engine (tier first, then minq): one server for quick_tps --depth 30000, one server for --depth 60000, one server
for lookup_ab.py --depth 30000. Not alternated.

## Results

Fresh prefill (code prompt):

| Engine | 30k prefill tok/s (29,984 tok) | 30k mean decode | 60k prefill tok/s (59,953 tok) | 60k answers |
| --- | --- | --- | --- | --- |
| tier | 345.4 | 43.6 | 255.0 | 1 token (code, prose, bash) |
| minq | 344.1 | 43.4 | 254.4 | 1 token (code, prose, bash) |

60k details: prose / bash 512-token prefill 164.5 / 160.5 (tier), 165.0 / 160.6 (minq); every 60k request reports
"decode 0.0 tok/s (1 tok)".

lookup_ab at 30k (notebook means): quote 75.9 (tier) vs 72.9 (minq), edit 68.1 vs 68.7, plain 43.4 vs 43.3. One quote
item per engine answered 1 token: csv.py (tier) and textwrap.py (minq), both sha 4f53cda18c2b, n 1, wall ~92 s. The
notebook quote means include the 1-token items as 0 tok/s.
Receipt detail: the fnmatch.py edit at 30k gave 2048 tokens (sha bbf7b9093069) in both engines.

## Deviations, incidents, void runs

- Every fresh 60k request (59,953-token prompt, then the prose and bash prompts at that depth) answered with 1 token,
  in both engines. Earlier: P50 at 120k had csv.py answer 1 token in both arms (bin-lookup). Extended sweeps that grow
  the prompt step by step (P40c, P56: 4k -> 32k -> 64k -> 96k) had none.
- Lead written at the time (not proven): "the failing prompts are fresh and longer than 32,768 tokens = the preset's
  GGML_CUDA_FA_PREFILL_F16 cap; the f16-converted and the in-place attention paths switch within one prefill."
  P64 disproved this lead (f16 off fails too); P64's pool-off arm found the cause: the shared CUDA pool.
- The 30k means compare different item sets (2 of 22 items were 1-token). P70 reran the set with the pool off.

## Verdict

No gate. The min-Q prefill result is neutral (within 0.4 %). The decode data are confounded by the 1-token items.
The run is the first record of the 1-token bug on fresh long prompts.

## Corrections later

- P64: the bug is not f16 prefill and not lookup; the shared CUDA pool (patch 0037, GGML_CUDA_SHARED_POOL set by the
  8 GB preset) is the cause. P68 / P69: patch 0045 (poolsync) fixes it.
- P70: clean min-Q set with the pool off (neutral on Turing).
- Notebook P67 result counts the pool-on runs that failed: "P61 (2 servers), P64 (4), P67 graphs-off (1) = 7 of 10".

## What it changed

Opened the 1-token investigation (P64 plan at the front of the queue). Speed data was later replaced by P70 for #330.

## Toolbox

- Method: a fresh long prompt (one prefill past every internal threshold) finds bugs that step-by-step sweeps miss.
  Always add one fresh-long-prompt arm to release checks (this became the "fresh 60k x2" arm of every release check).
- Count 1-token answers (n == 1) in every receipt; a 1-token answer is a failure, not a fast answer.
- Model-specific: none for the method. The bug itself depended on the MTP draft context sharing a CUDA pool.
