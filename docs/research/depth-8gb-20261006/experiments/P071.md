## Question

Why did restoring a mid-message checkpoint (P59, N=8192) give identical wrong texts for different prompts? Which
component (MTP / lookup rollback planes, GDN state gather, the tiered KV redirect / prefetch) is at fault?

## Why

P59 (2026-10-08 15:24): wall per request after the first fell from 272-294 s to 45-58 s, but all 3 plain prompts gave
one identical text (sha c5f73752f40a) and all 4 edits gave one identical 2048-token text (sha bbf7b9093069).
Agent code read before P71: "--checkpoint-every-nt bookkeeping is correct (n_tokens = batch start, restore sets
n_past = P, keep_first(P), seq_rm(P,-1), tail re-processed). N=0 never restored a deep recurrent checkpoint, so the
fault is in the deep-restore path itself (also reachable by long multi-turn chats)."

## Plan and gate

Notebook: "One change per arm, bin-ckpt, PR-merged launcher copy (lookup on, no pool), LLAMA_ARG_CHECKPOINT_EVERY_NT=
8192, lookup_ab.py at 64000: a) control, LLAMA_ARG_LOG_VERBOSITY=4 (read "restored context checkpoint ... n_past")
b) BONSAI_SPEC=0 (no MTP, no lookup, no rollback planes) c) GGML_GDN_STATE_GATHER=1 d) GGML_CUDA_KV_TIER_REDIRECT=0 +
GGML_CUDA_KV_TIER_PREFETCH=0. Wrong-output test: plain items (3 different prompts) with one identical sha, or edit
items with one identical sha. Reading: the arm that turns the output correct names the component."

## Method

4 servers in order (ctrl, nospec, gather, notier), lookup_ab.py at depth 64000 each (11 items; the first request
prefills ~64k, later requests can restore a checkpoint). Distinct-sha count per kind per arm. Checkpoint lines from the
server log (ctrl).

## Deviations, incidents, void runs

- Note on the notebook range "18-58 s": in every arm the first edit request (textwrap.py) also takes ~280 s, because
  the edit prompts start with a tool list and diverge from the quote/plain prefix early (lookup_ab.py sorts tool
  requests last for this reason). The range in the notebook covers the other requests of the ctrl arm.
- Root cause of P59 (found by timestamps): P59 ran at 15:24 with the launcher copy that still set
  GGML_CUDA_SHARED_POOL=1 (removed 16:50). The identical wrong edit text bbf7b9093069 also appeared in pool-on runs
  P60 (16k shlex.py edit, round 2) and P61 (30k fnmatch.py edit): the pool race, not the checkpoint restore.

## Toolbox

- Lever: checkpoints inside one long message (every N tokens at batch starts) for hybrid recurrent models. Without
  them a prompt that diverges inside a long message re-prefills everything (here 272-294 s at 64k); with N=8192 the
  restore cuts it to 18-58 s.
- Model-specific: Bonsai 27B has 48 GDN (recurrent) layers; their state cannot be truncated, so the server needs a
  saved state near the divergence point. Each checkpoint is ~168 MiB of host RAM at 64k (this matters on 16 GB RAM
  machines: issue #16).
- Method: when a fix gives wrong output, check what else was on during the run (here the pool race) before you blame
  the fix. A "one change per arm" isolation with a distinct-sha test is cheap.
- Transfers to any hybrid (Mamba / GDN / RWKV + attention) model served with llama.cpp-style checkpoints.
