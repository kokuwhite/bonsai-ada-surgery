## Question

Does product-sparse build and pass op tests on sm_75? With the launcher-sparse defaults (graphs on, packed mask on,
lookup on, page bounds counted in the line), where does sparse beat dense?

## Why

Step 3 of the sparse bundle plan on #21 (item 1): the 4070 pushed product-sparse 3ab0af3c2 and launcher PR #49 and
asked for "P121 again on this build (96k / 128k, MIN_HOST=0 set by hand) for the crossover". 0053 (graphs on below
the line) and the launcher line both change the dense arm, so P121's crossover needs a repeat.

## Plan and gate

Script header: "Crossover arms (one server each, 96k -> 128k): dense = BONSAI_SPARSE=0; sparse0 = launcher default +
MIN_HOST=0 by hand. Reading (declared before the run): decode ratio at 96k / 128k -> MIN_HOST = host tail at the
first depth with >= 1.05x. Gates for the build (before the arms): FLASH_ATTN_EXT and GATED_DELTA_NET op tests pass,
else stop."

## Method

Build 3ab0af3c2 for 75-real inside the job; test-backend-ops -o FLASH_ATTN_EXT and -o GATED_DELTA_NET; then two arms,
one server each (dense 20:33, sparse0 20:53): quick_tps 96000 then 128000, a 10 s trace, the launcher kv lines, and
counts of sparse_mask and graph-switch log lines.

Reading (notebook): "accounting works (a little generous); the reserve costs ~14k cells at every depth, which eats the
96k gain; dense much stronger with graphs + lookup + bigger line. Predicted P123 2 % gate fail from the line, not
routing." Exact cost: 62,464 - 48,640 = 13,824 cells.

## Deviations, incidents, void runs

- Like P121, the 128k step was a full prefill (127,340 tokens evaluated) in both arms, not an extend.
- With lookup on, single items move a lot (dense 128k bash 29.1 vs prose 15.5). Three items per depth is a small
  sample for a ratio near 1.
- The 2,237 / 2,577 graph switch lines show CUDA graphs on (0053) in both arms; the sparse arm needed no
  DISABLE_GRAPHS.

## Verdict

DONE. Build gate PASS. Crossover: 96k 1.02x (below the 1.05x rule), 128k 1.17x. With this launcher the line cost, not
the kernel, decides the shallow-to-mid depths.

## Corrections later

The 4070 answered on #21 (6159428007): the reserve must cover the full 262k window, because the line is fixed at load;
reserving only beyond MIN_HOST saves ~2k cells; bounds in pinned host memory cost ~18 ms per token; page 128 has no
quality data. Their pick, int8 bounds at page 64 (514 B per host cell), gives ~7k cells back (c8bbb1898; P127 / P128).

## What it changed

- Posted on #21 with options (bounds only beyond MIN_HOST, page 128, bounds in pinned host memory). The 4070 chose
  int8 bounds (events E30, E31).
- The routing check (P123) was predicted to fail its 2 % gate because of the line, not the routing.

## Toolbox (for the next model)

- Transfers: a reserve sized for the whole window costs line cells at every depth. On 8 GB at 262k, 244 MiB of f16 page
  bounds = 13,824 cells = the whole 96k gain of sparse.
- Method: post the launcher's kv lines and trace min free per arm; the reserve can be checked against the trace (here
  195 vs 70 MiB at 128k: the tables fill only as the host tail grows).
