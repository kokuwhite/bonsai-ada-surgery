## Question

Is there more speed above +1000 MHz memory, and which step is stable under sustained server load with byte-identical
greedy output?

## Why

P38: +1000 = +7.7 % plain decode. "P39 (plan): speed at +1250 / +1500 (GDDR6 error retry shows up as a speed drop),
then a soak on the best stable step: server, greedy, 4k/16k/32k prompts x reps, outputs compared byte-for-byte with
stock; any divergence -> step down."

## Plan and gate (as frozen before the result)

P39b: "One server, launcher 8 GB preset auto (drafting mode), bin-rc3, BONSAI_LAYER=0. Clocks switched live: stock
6 min (reference texts) -> +1000 10 min -> +1250 10 min -> stock 4 min. p9_soak: depths 4k/16k/32k, two prompts, 300
tokens. Gates per step: every text byte-identical to the stock text of the same (depth, prompt); no driver reset
(System log nvlddmkm 4101/13/14 or bugcheck); decode last-2-min within 2% of first-2-min. Pass -> that step is offered
in docs as an opt-in with this receipt (never a launcher default: clocks are the owner's hardware choice)."

P39c: "+1000 for 60 min between two 8-min stock references, same launcher/prompts; gates as P39b (identical texts, no
nvlddmkm event, drift < 2%)."

## Method

p9_soak.py: warm both depth prefixes, then loop depths 4k -> 16k -> 32k; the prompt alternates per cycle between
"Write a Python function that merges overlapping intervals..." and "Explain how a heat pump works in winter...";
300 tokens, greedy, thinking off. GPU telemetry (core clock, temperature, power, throttle reasons) every second.
Clocks switched live with the BonsaiAB_P3 / P<slot> tasks while the server ran.

   Full entry in the events file.
2. P39b first attempt void (receipts/p39b_void): "serve.ps1 used the main checkout launcher (12 GB, no preset) ->
   negative VRAM line, never served". All four phases got "connection refused". Rerun with a temporary copy of the

3. P39b +1250: GPU fault after ~10 min under load (13:23, nvlddmkm 14 + 153; server "CUDA error").
4. P39c attempt 1 killed at 13:37:48. First cause found: "the Claude app restarted this session's process at 13:38
   (claude.exe --resume, new process tree), and every job started from the tool shells died with it." Long GPU jobs
   moved to the BonsaiJob scheduled task (jobrun.sh). Relaunched detached via Start-Process at 14:08, then as BonsaiJob
   at 14:20.
5. P39c attempt 2 died ~1 min after the live switch to +1000. Notebook: "Both P39c deaths (13:37 and 14:31) came
   seconds after Afterburner switched profiles under CUDA load ... So the "app restart" cause above is at best part
   of it: a live memory-clock switch can kill the server. P39b's one live switch survived."
6. Notebook: "P39c note: a 34 s incremental dev build ran at 14:07 during the +1000 phase (CPU load; texts unaffected,
   decode drift reading around 14:07 discounted)." No +1000 phase is recorded at 14:07 (attempt 1 died 13:37:48;
   attempt 2 was relaunched at 14:08 / 14:20). The timeline of this note does not match the other entries.
7. Receipt findings not in the notebook:
   - receipts/p39c/stock_b.json (12 requests, written 14:31:48, no GPU samples) overlaps in time with stock_a.json
     (14:23-14:30:38). Two soak processes ran against one server. The most likely reading: the 14:08 Start-Process
     instance was not stopped; the 14:20 BonsaiJob's stop.ps1 killed its server, its +1000 phase failed, and its
     stock_b phase then ran on the BonsaiJob's new server. Its 12 texts match stock_a (12 / 12).
   - receipts/p39c/clocks.txt has five readings (both attempts); one shows a 215 W power limit, the others 175 W. The
     file mixes the attempts, so this reading cannot be tied to one switch.
   - The "drift" readings are an artifact of the method. p9_soak alternates the two prompts per cycle, so "first 2 min"

     at 239 s and 479 s are 55.62 and 56.08 (no fall).

## Verdict

- P39a: +1250 = +8.9 % in llama-bench; +1500 crashes the PC. "Rule from here: memory steps above +1250 are not tried
  again on this card; +1250 itself needs the soak before any use."
- P39b: "+1250: FAIL - GPU fault under sustained load (also the +1500 bugcheck)." "+1000 passes 10 min, identical
  outputs." "Slots now: 1 = +500, 2 = +1000; nothing above +1000 staged. +1000 needs a longer soak (60 min, stock
  reference before and after) before docs mention it; it is never a launcher default."
- P39c: void twice. "P42 (plan): set the clock with no server running, then start the server."

## Corrections later

- 2026-10-07 correction (events file): the branch launchers do not read BONSAI_BIN, so P39b and P39c ran
  bundle-20260927, not bin-rc3. The drafting mode's verify step is 2 columns, and #325 changes only the 1-column path,
  so drafting decode is the same on both engines (P40c); the stability verdicts stand.
- P42: +1000 passed 60 min with the clock set before the server started.

## What it changed

Afterburner slots rewritten (nothing above +1000 staged). Rule: never switch clocks while a server runs. Memory-clock
cap +1000 on this card (also in Cary's memory notes: re-apply slot 5 after reboots).

## Toolbox (for the next model)

- Method: soak with byte-identical greedy text against a stock reference, plus driver event checks. Speed alone hides
  instability (+1250 ran clean in llama-bench and faulted after 10 min in the server).
- Transfers: never step a memory clock past a known-good value while the server runs, and never test steps far past
  the spec on a machine you cannot afford to crash. For drift gates, compare the same prompt with itself; an
  alternating prompt mix creates fake drift. Run long jobs outside the agent app's process tree (scheduled task), and
  make sure an earlier instance is stopped before you start a second one.
