## Question

Is the 262k default stable and correct to the end of the window, and what are decode and prefill there?

## Why

Cary: "quality and stability up to the end of the window."

## Plan and gate

P86 (notebook): "test launcher (branch 8gb-262k), bin-pmask, auto-sized, quick_tps 4k/64k/128k/192k/250k (each extends),
VRAM trace. Record decode/prefill per depth, acceptance, one-token. Gates (for the PR claim "to the end of the
window"): server up to 250k, 0 one-token, trace min >= 60 MiB."
P86b (notebook, in the P86 result): "Next: P86b (queue 53zz) 128k -> 192k -> 250k with QTPS_TIMEOUT 7200
(bench/quick_tps.py now reads it) for the full-window decode number."

## Method

P86: one server, quick_tps at 4000, 64000, 128000, 192000, 250000 (each step ~58-64k new code tokens), trace every 10 s.
P86b: one server, quick_tps at 128000 (fresh 127,340-token prefill), 192000, 250000.

## Deviations, incidents, void runs

- P86: client timeout (1800 s) too short for the 250k step. quick_tps got QTPS_TIMEOUT for P86b.
- P86 and P86b ran with different VRAM lines (59,392 vs 57,600: free VRAM at start differs with the desktop).
- The README card was published (PR #17, "5.7 tok/s at 250k") from P89's 250k reading (chunked prefill engine, 5.7)
  before the P86b result was logged; P86b then gave the same 5.7 on the non-chunked engine.

## Verdict

P86 gates: server up to 250k - yes (the server stayed up; the client timed out); 0 one-token - yes; trace min 116 >= 60 -
yes. P86b gives the full-window decode: 5.7 tok/s at 250k. The deep-prefill weakness (25.4 tok/s at 250k for bulk
input) is a finding, not a gate.

## Corrections later

- P89 (chunked flash attention for prefill): code prefill 171.1 / 116.0 / 90.3 at 128k / 192k / 250k (P86 121 / 58,
  P86b 25.4). Shipped as patches 0051-0052 (PR #19, bundle-20261010).
- 2026-10-10 P103 note: "P102 dense ran graphs off and got 5.7 tok/s at 245k = P86b with graphs on".
- P98b: decode at depth is PCIe 3.0 bound (~11 of ~13 GB/s used at 250k).

## What it changed

Supported the PR #13 claim to the end of the window; gave the 250k number for the README card (docs/img/card8gb.png,
PR #17); started the chunked-prefill engine work (P89).

## Toolbox

- Method: sweep to the end of the window with a trace and a long client timeout; record bulk prefill past the staged
  depth separately from short-turn prefill (512 tokens).
- Finding: past N+S, bulk prefill reads host rows once per query tile; a 58k paste at 192k-250k takes 30-38 min on
  PCIe 3.0 without chunking. Short agent turns stay usable (~15 s per 512 tokens at 192k).
- Transfers to any 8 GB card with a long window: decode at the end of the window is set by PCIe bandwidth.
