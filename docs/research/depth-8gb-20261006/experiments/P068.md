## Question

Does the poolsync engine (each graph waits for an event after the other stream's last graph in shared-pool mode)
remove the 1-token answers on Turing, and what does it cost in decode speed?

## Why

P64 / P67: the shared pool race. The 4070 session wrote 142d5105d; it was untested on Turing.

## Plan and gate

Notebook: "Build sm_75 -> bin-poolsync. Pre-hotfix launcher copy (pool on), drafting preset + lookup: fresh 60k
quick_tps x3 (separate server starts), lookup_ab.py 30000. Gates (4070 session): 0 one-token answers -> ship as patch
0045 and the pool returns to the preset (+62 MiB); any failure -> pool stays off. Also record decode vs bin-tier (a
graph-boundary wait can cost speed)."

## Method

Build, then 3 separate server starts with a fresh 60k quick_tps each, then one server with lookup_ab.py at 30000.

None. Because the bug is intermittent (P67), 0/9 alone was not proof; P69 ran the alternated test.

## Verdict

Gate pass (0 one-token). Decode not slower: 31.6 vs pool-on control 31.3 (P67) and pool-off 29.1 (P66).

## Corrections later

P69 confirmed: poolsync 0/18 vs 8a6d2ea12 18/18. Shipped as patch 0045 (bundle-20261008-8gbfix, P72b).

## What it changed

Patch 0045 candidate confirmed on Turing. The pool return on 8 GB waited for P83.

## Toolbox

- Lever: a shared CUDA memory pool between the target and draft contexts saves VRAM (~62 MiB here) but needs a
  cross-stream ordering (event wait at graph boundaries). The wait cost no measurable decode here.
- Transfers to any engine with two CUDA streams sharing one allocator.
