## Question

Past the VRAM line each decode step reads host rows over PCIe. Do 2 MTP draft tokens past the line (tail 2) pay more
at ~200k than they cost in VRAM cells (one 150 MiB rollback plane)?

## Why

Notebook: "P47 (131k) measured tail 2 +9 % at 126k but -9..-41 % mid-depth (one 149.6 MiB plane = ~8.7k positions less
in VRAM). At 200k each PCIe-bound step is longer, so extra verify columns may pay more (4070: +26 % on code at 180k)."

## Plan and gate

P80 (notebook): "Arms, drafting preset + lookup, bin-0046, BONSAI_CTX=262144: tail 1 N=41,472 (preset) / tail 2
N=32,768; quick_tps 64k then 200k (each extends). Reading: decode at 200k (code/prose/bash) and 64k; gate for a
depth-only tail 2: +15 % at 200k with <= 5 % loss at 64k. Public data (27B) -> PR/issue comment."
P80 amendment (after P75): "P75 showed the 262k preset (staging on, N 41,472) goes below zero free VRAM at depth, which
would confound tail 1 vs 2. Both arms now use staging off (P77 setting): tail1 N 54,784, tail2 N 46,080 (same 8,704 cell
difference as before), with the VRAM trace. If P77 shows staging off is unsafe, P80 is re-planned."
P80 stop (P81 plan entry): "P80 (tail 2 at 200k) waits for this engine; it ran 2 minutes on the over-committed N and
was stopped."
P80b (notebook): "(4070 suggestion, re-planned on the new engine): same launcher, 64k and 200k, tail 1 (auto N) vs
tail 2 (BONSAI_SPEC_DEEP=2, BONSAI_VRAM_MARGIN 375 = 225 + one 150 MiB rollback plane). Data only; tail 2 must beat
tail 1 at 200k by > 5 % to change anything."
P80c (notebook): "same with bin-chunk C=32768 and timeout."

## Method

Each arm: one server, quick_tps at 64000 then 200000 (the 200k step adds ~135k new tokens), free VRAM every 10 s.
Order tail1 then tail2.

## Deviations, incidents, void runs

- P80: started at 12:41 on the P77 "staging off, N 54,784, 262k" setting, which P77 (finished 12:37) had just shown to
  over-commit (load free 185, trace below zero). Stopped after ~2 minutes; re-planned on the partial-staging engine.
- P80b: quick_tps had no long timeout for the 200k step (~135k new tokens at ~35-58 tok/s past the staged depth).
  QTPS_TIMEOUT existed from P86b on; P80c set 7200 and used chunked prefill so the step fits.
- Acceptance notebook values "0.80" / "0.70" for P80c are the receipt's 0.799 / 0.702 rounded.

## Verdict

P80c: tail 2 +17 % at 200k (> 5 % threshold of P80b) but -10 % at 64k. It fails the P80 gate for a depth-only default
("+15 % at 200k with <= 5 % loss at 64k": the 64k loss is 10 %). Decision: tail 1 stays the default; tail 2 is a
documented option for sessions that stay past ~150k.

## Corrections later

- P97 / P98b (2026-10-10) list "more verified tokens per host read (tail 2 = +17 % at 200k, -10 % at 64k ...)" among
  the remaining depth levers. PR #20 merged: docs/8GB "Sessions that stay deep" (tail 2 data).

## What it changed

Docs: BONSAI_SPEC_DEEP=2 documented for deep sessions (PR #20). Default unchanged.

## Toolbox

- Lever: number of MTP draft tokens allowed past the VRAM line. Each extra draft needs a rollback plane (~150 MiB here
  = ~8.5k VRAM cells), so it trades shallow speed for deep speed.
- Model-specific: one MTP head (Bonsai 27B); acceptance falls from ~0.80 (tail 1) to ~0.70 (tail 2); plane size from
  the 48 GDN layers' recurrent state.
- Transfers: past the VRAM line decode is bandwidth (PCIe) bound, so verifying more tokens per host read pays; near
  the line, VRAM cells pay more. Choose by the depth the session stays at.
- Method: give deep steps an explicit client timeout (a 135k-token step past the staged depth can take > 30 min
  without chunked prefill).
