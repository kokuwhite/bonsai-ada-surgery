## Question

Where does prefill time go on our Turing build (FLASH_ATTN_EXT vs PTQ1_0 MUL_MAT vs GDN vs the rest), and which bucket
does sudoingX's build do differently?

## Why

P013: our prefill is below sudo's at every depth. Code read in the plan: on Turing our prefill already uses the in-place
quantized-K/V MMA kernel, so no f16 copy; "sudoingX's fork converts K/V to f16 per chunk and runs f16 MMA. Switching
ours to the convert path would reserve f16 K+V for the full window at load (~512 MiB at 131k = ~30k q4_0 positions) -
rejected for 8 GB on arithmetic alone. Profile instead."

## Plan and gate

P16: "bin-p12, no head, N=58112 (no memory pressure), GGML_CUDA_OP_TIMING=1 + LLAMA_ARG_LOG_VERBOSITY=5, one fresh 32k
prefill. Read the per-op table: FLASH_ATTN_EXT vs MUL_MAT (MMQ) vs GDN vs the rest. The largest bucket that sudo's build
does differently is the kernel target." No numeric gate.
P16b: "N=67840 (60k inside the VRAM line, 395 MiB free in P14c), one fresh 60k prefill (~117 ubatches), same env."

## Method

run_arm.sh with a single depth (32000 for P16, 60000 for P16b). With no prior request at that depth the code prompt
evaluates the whole filler. The op-timing table is grepped from the server log.

## Deviations, incidents, void runs

- P16 void: "The op-timing table prints every 100 timed (non-CUDA-graph) graphs; decode runs as CUDA graphs, so only
  prefill ubatches count and a 32k prefill is 64 of them - no table." P16b used a 60k prefill (~117 ubatches) to pass
  100.
- P16b ran at N=67840 so that 60k sits inside the VRAM line.

## Verdict

"prefill at parity when there is no memory pressure; where prefill time goes." Attention (in-place q4_0) is ~40% of
prefill at 60k; PTQ1_0 mat-muls ~44%; GDN 7.5%.

## Corrections later

- The "-3% vs sudo at 60k" compares a fresh 60k prefill (59,953 tokens evaluated, positions 0-60k) with sudo's 60k
  number from the quick_tps sequence (28,425 tokens evaluated, positions ~32k-60k, all deep). P023 showed that the
  sequence decides the number: on the same sequence our incremental long-mode prefill was 201 vs sudo 256 at 60k
  (-21%, P020/P023). The notebook does not mark P16b as corrected, but P023's conclusion supersedes its "parity" claim.
- P025: the attention bucket was the lever: f16 conversion for prefill batches only, buffer from the pool at the actual
  KV length, gave +18% (32k) and +26% (60k) incremental prefill.
- 2026-10-08 P064 (outside this range) notes "no-head fresh 60k worked (P16b, old engine)" as a control for the
  one-token bug.

## What it changed

Named FLASH_ATTN_EXT on in-place q4_0 K/V as the prefill target that sudo's build does differently; led to P025.

## Toolbox

- Method: GGML_CUDA_OP_TIMING prints only non-graph runs and only every 100 graphs: profile prefill with enough ubatches
  (> 100), and decode with GGML_CUDA_DISABLE_GRAPHS=1 (P036b, outside this range).
- Finding: on this hybrid model at 60k, prefill time is ~40% attention, ~44% ternary mat-mul, ~7.5% GDN.
- Model-specific: 16 attention layers (x16 FLASH_ATTN_EXT), 46-48 GDN layers, PTQ1_0 shapes 5120x17408 etc.
- Transfers: compare prefill only across identical request sequences; a fresh prefill and an incremental one differ.
