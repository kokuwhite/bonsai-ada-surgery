## Question

Is decode on the current engine bandwidth-bound enough that a memory overclock pays?

## Why

"The 2026-10-06 memclock sweep ran on the pre-#325 engine at ~36 tok/s with 5% stock-to-stock drift: inconclusive.
Now mat-vecs are 72% of the step at 80% of peak." (P36b/P37c)

## Plan and gate (as frozen before the result)

"Afterburner slot 1 = mem +500, slot 2 = mem +1000 (power 100%, fan 100), slot 5 stock. bin-rc3 llama-bench tg256
-r 3, order 5/1/2/5/1/2, clocks sampled during each run.
Gate: +1000 beats both stock runs by > 4% (half of the +14% bandwidth) -> decode is bandwidth-bound and memory OC is
back in play (then a stability soak with output compare before any default); < 2% -> ALU/latency-bound, closed."

## Method

For each step: apply slot 3 then the target slot, sample nvidia-smi every 2 s (memory clock, core clock, power,
temperature, power limit), run llama-bench tg256 x3, record the mean and spread.

## Results

| order | slot | memory offset | tg256 tok/s |
| --- | --- | --- | --- |
| 1 | 5 | stock | 46.24 +- 0.03 |
| 2 | 1 | +500 | 48.16 +- 0.09 |
| 3 | 2 | +1000 | 49.80 +- 0.12 |
| 4 | 5 | stock | 46.16 +- 0.18 |
| 5 | 1 | +500 | 48.14 +- 0.04 |
| 6 | 2 | +1000 | 49.72 +- 0.14 |

+500: +4.2 %; +1000: +7.7 % (vs the stock mean 46.20).

Clock samples (receipt clk_*.txt; columns: memory clock, core clock, power draw, temperature, power limit):

| step | first sample (before load) | under load |
| --- | --- | --- |
| stock (clk_983, clk_30107) | 7000 MHz mem, 1470 MHz core, ~40 W | 6801 MHz mem, core 1845-1905 MHz, 171-177 W, up to 61 C |
| +500 (clk_16813, clk_21543) | 7500 MHz, 1470 MHz | 7300 MHz, core 1830-1875 MHz, 170-178 W, up to 62 C |
| +1000 (clk_19456, clk_18319) | 8000 MHz, 1470 MHz | 7800 MHz, core 1815-1845 MHz, 169-177 W, up to 62 C |

"Under load" = samples with power draw above 150 W. The table's "maxmem 7001 MHz" column is `clocks.max.mem`, which
does not show the offset.

## Deviations, incidents, void runs

- The clock files are named `clk_<random>.txt`: the script writes `clk_$s_$RANDOM`, and `$s_` is an unset variable,
  so the slot number is lost. The files map to steps by their memory clock and by file time.
- Notebook text vs receipt: the notebook says "Memory clock under load 7000 / 7500 / 8000 MHz (14 / 15 / 16 Gbps),
  core 1470 at 175 W". In the receipts, 7000 / 7500 / 8000 MHz and core 1470 MHz are the first sample of each step,
  before the load starts (~40 W). Under load the memory clock reads 6801 / 7300 / 7800 MHz and the core 1815-1905 MHz.
  The offsets (+500 / +1000) are the same in both readings.

## Verdict

"Gate PASS." "memory +1000 = +7.7% decode on the current engine - the old "memory OC does nothing" is void."
"docs/8GB.md "Not used: memory overclock" is wrong for the planar-PT engine (that sweep ran before #325). Fix the doc."

## Corrections later

- P39a/P39b: +1250 is +8.9 % in llama-bench but faults under sustained load; +1500 crashed the PC (events file).
- P42: +1000 is stable for 60 min with the clock set before the server starts; +2.4-2.7 % in the drafting preset
  (drafting is less bandwidth-bound than plain decode).

## What it changed

Docs fixed in PR #12 (2026-10-09): memory clock moved from "Not used" to "Optional" (+500 +4.2 %, +1000 +7.7 % in
llama-bench). Never a launcher default.

## Toolbox (for the next model)

- Lever: memory clock on a bandwidth-bound decode. Re-test a "does nothing" result after any kernel change that moves
  the bottleneck.
- Method: llama-bench (no server), alternated stock / +500 / +1000 twice; the expected gain is about half the
  bandwidth gain when mat-vecs dominate.
- Transfers: read clocks under load, not the first sample. A speed test is not a stability test: soak with
  byte-identical output before any use (P39, P42).
