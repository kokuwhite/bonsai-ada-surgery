## Question

Can prefill past the f16 limit (32,768 cells) and past the staged depth be made 2-3x faster by splitting attention
over the KV dimension into VRAM-sized f16 chunks with an exact softmax merge, without changing quality?

## Why

Notebook (P89 design): "Cary: 30 min for a 58k paste at 192k is unusable. Two causes: (1) f16 prefill (fast MMA) only to
32,768 cells (the f16 copy of the whole cache does not fit VRAM): 512-token prefill 262 tok/s at 32k -> 100 at 128k;
(2) past the staged depth, host rows are read in place by every query tile: 35 tok/s at 192k."
"Fix: GGML_CUDA_FA_CHUNK=C: prefill-sized ops split the KV dimension into chunks of C cells; per chunk: copy to VRAM
(pool), convert to f16, f16 MMA kernel, keep (row max, row sum, output); fold chunks with the exact softmax merge.
VRAM bounded by one chunk. Worktree prism-chunk (branch fa-chunked-prefill on d90e35528), implementation by an agent
(build only, no GPU). Gates before any speed claim: test-backend-ops FLASH_ATTN_EXT pass with a small C (256) incl.
q4_0 K/V and the packed mask; server texts identical (chunk off vs 32768) at 64k with drafting + lookup (22 items).
Expected: prefill past 32k ~2x, past the staged depth ~3x."

## Plan and gate

P89 (notebook): "Engine prism-chunk 9f68d0011 + tests d0c1d8644 (agent; build passed, 509/509). Design: per chunk of C
cells (multiple of 256): copy the chunk's quantized K/V from the tiered VA to a pool buffer when it reaches host pages,
f16 convert, f16 MMA with stream-k off (every tile writes partial + (max, rowsum) via the needs_fixup path), fold kernel
into a running result; last chunk normalizes. Chunked ops leave the tier prefetch list. Fallbacks: < MIN_Q queries, KV
not a multiple of 256, unquantized K/V, sinks/ALiBi/softcap, multi-sequence, other head sizes, pre-Turing.
Arms (bin-chunk, 262k test launcher): test-backend-ops FLASH_ATTN_EXT base / C=256 / C=768 / C=256 MIN_Q=1 hs256;
lookup_ab 64k chunk off vs 32768; quick_tps 4k/64k/128k/192k/250k with C=32768 (same sequence as P86; QTPS_TIMEOUT
7200). Gates: all tests pass; 64k texts >= 9/11 same (known depth spread; P25 f16 prefill was byte-identical, so 11/11
is the expectation); 0 one-token; trace min >= 60 MiB; code-prompt prefill vs P86 (234 / 121 / 58 at 64k/128k/192k)
faster by >= 1.5x at 128k and 192k. Decode must not change (+-2 %)."
P89b (notebook): "N pinned 45,056 (room for a whole-cache f16 copy at 64k); whole-cache f16 (FA_PREFILL_F16=65536) vs
chunked f16 (C=32768), same bin. Gate: 11/11 identical -> the merge is exact and the P89 diffs are the
f16-vs-dequant difference already accepted below 32k (P25). Less -> study the merge."
P89c (notebook): "perplexity at a 64k window (wikitext-2, 2 x 65,536), in-place / whole-f16 / chunked; a merge that is
only rounding gives the same PPL as whole-f16 within the +/- band (expect <0.1 %)."

## Method

P89: tests (4 runs; stop if any FAIL); two servers for lookup_ab at 64000 (chunk off, then 32768); one server for the

- Texts: 8/11 (gate >= 9/11) -> not met as written; resolved by P89b (merge not bit-identical) and P89c (PPL equal:

## Toolbox

- Lever: chunked flash attention over KV for prefill (flash-decoding style split along KV + exact log-sum-exp merge).
  VRAM cost is one chunk (here 32,768 cells as f16), independent of depth. It lets the fast f16 MMA kernel run at any
  depth and turns host-row reads into one bulk copy per chunk.
- Quality method: when a "should be exact" change alters near-tie greedy texts, measure perplexity on a long window
  against both the old path and a reference path (whole-cache f16). Same PPL within the band = rounding.
- Model-specific: head size 256, GQA 6, q4_0 K/V, 16 attention layers; fallbacks for other shapes.
- Transfers to any model with long-context prefill on a small card, and to any GPU (Ada gained +12-14 %).
