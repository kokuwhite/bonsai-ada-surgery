## Question

On the same binary and the same 262k launcher, how many more cells does q3_0 put in VRAM than q4_0, how much faster
is decode past the line, what does it cost below the line, and does quality hold at 160k?

## Why

P108: q3_0 kernels are exact (op tests pass) and PPL costs +0.56 % at 16k, +0.03 % at 64k, for 14,336 vs 18,432 B
per position (-22 %). The depth gain was an estimate only (line ~+28 %, PCIe bytes -22 %).

## Plan and gate

Notebook (P108 entry): "P114 (queue 69g4, gate in its header): same binary, q4_0 vs q3_0 sweep 4k/64k/128k/192k +
q3_0 160k copies/needles. Pass: line >= 1.2x, decode >= 1.05x at 128k/192k, 4k within 3 %, 0 one-token, min free >=
60, needles 12/12, copies >= 9/10."

Script header: "Gate (declared here, before the run): q3_0 VRAM line >= 1.2x the q4_0 line; decode q3_0 >= 1.05x
q4_0 at 128k and 192k; 4k within 3 %; 0 one-token; trace min free >= 60 MiB; 160k q3_0 needles 12/12 and copies >=
9/10 (P105 dense q4_0: 12/12, 10/10). Note: this engine has no patch 0053 and no sparse; both arms share that."

## Method

Two speed arms on one binary, one server each: speed_q4 (15:16-15:51), then speed_q3 (15:51-16:25). Each runs
quick_tps at 4000 -> 64000 -> 128000 -> 192000 (code, prose, bash per depth, 400-token greedy decodes) with a free-VRAM
sample every 10 s. Then two fresh q3_0 servers at 160k: exact code copies (10 functions, code_needle.py) and needles
(12 vaults, needle_depth.py), as P105.

## Deviations, incidents, void runs

- The 192k step was a full prefill (191,010 tokens evaluated), not an extend: the 128k step was an extend (63,847
  tokens). Both arms did the same, so the A/B holds. The notebook gives the 191,010 count.
- The q3_0 quality phase (code copies 16:25-16:42, needles 16:42-16:57) ran while the P116 engine e63ce36d9 built
  (build ok 16:56:16, receipts/build-0054.txt; the notebook says the build started 16:3x). Copies and needles are
  pass / fail scores and are not affected; the tg values in code.jsonl are not speed readings.
- The 64k -6.5 %: both arms hold 64k almost fully in VRAM (lines 62,720 / 82,176). The notebook reads it as the q3_0
  dequant cost inside the attention kernel. No op timing isolated it in this run.
- The quality reference (P105) is q4_0 on another engine. No q4_0 quality arm ran on bin-q3kv.
- The 2060 posted this as "PASS on every gate" on #21 at 21:58Z (16:58 rig time), with the same numbers.

## Verdict

PASS. Notebook: "Gates all PASS (line 1.31x; 1.23x / 1.15x; 4k -0.9 %; quality; min free). 64k -6.5 %: both nearly
all in VRAM there, so it is the q3_0 dequant cost in the attention kernel (kernel work item)."

## Toolbox (for the next model)

- Transfers: a smaller KV type pays off past the VRAM line (more cells in VRAM, fewer PCIe bytes per step), and costs
  a little below it (dequant work in the attention kernel). Measure both sides of the line.
- Method: put the new type in the launcher's bytes-per-cell table before the run, so the line moves as it would for a
  user; compare on the same binary.
- Pitfall: check the evaluated token count of each step. A step meant as an extend can be a full prefill (here 192k).
