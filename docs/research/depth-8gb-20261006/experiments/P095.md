## Question

Can the CPU compute partial attention over the host-RAM rows of the KV cache fast enough to replace the PCIe read at
depth decode?

## Why

Cary: depth is the main priority. Notebook: "Decode past the VRAM line is PCIe-bound: 250k, N ~58k: 192k host rows x
18,432 B = 3.5 GB per step; 5.7 tok/s with MTP (~1.8 tokens per step) = ~3.2 steps/s = ~11 GB/s, near the PCIe 3.0
x16 limit. Per attention layer ~19 ms." Idea: the host rows are already in system RAM (~35 GB/s usable); the CPU
computes (row max, row sum, unnormalized V) for the host rows while the GPU does the VRAM rows, then the exact
softmax merge (as patch 0051). Risk: compute, GQA 6 = each K/V row used by 6 heads.

## Plan and gate

Notebook: "Step 1 (no engine change): test-backend-ops perf FLASH_ATTN_EXT on the CPU backend for our shape: q4_0
K/V, head 256, 4 KV heads, GQA 6, kv 32k/64k/128k/192k, 1 and 2 queries (worktree prism-cpuattn, branch
cpu-host-attn on fa-chunked-prefill). Gate to build it: CPU time per layer for 192k rows, 2 queries < ~12 ms (2/3 of
today's ~19 ms, leaving room for sync and merge). If the stock CPU op is slower, check a dedicated kernel (q8 query x
q4_0 K with AVX2 int8 dots, 6 heads per row load) before giving up."

## Method

test-backend-ops perf for FLASH_ATTN_EXT, one KV layer shape of this model (head 256, 4 KV heads, GQA 6 = nr23 [6,1]),
kv 32,768 / 65,536 / 131,072 / 196,608 cells, nb 1 and 2 queries. CPU backend (12 threads) and CUDA0 (K/V in VRAM:
an upper bound for the GPU, not the PCIe-bound host read). The tool's us/run is one layer.

## Results

ms per layer (us/run / 1000):

| kv cells | CPU nb 1 | CPU nb 2 | CUDA0 nb 1 | CUDA0 nb 2 |
| --- | --- | --- | --- | --- |
| 32,768 | 23.84 | 47.08 | 0.48 | 0.47 |
| 65,536 | 46.91 | 93.25 | 1.18 | 1.14 |
| 131,072 | 91.76 | 185.19 | 2.36 | 2.33 |
| 196,608 | 138.93 | 278.04 | 3.14 | 3.05 |

CPU throughput 33.78-35.11 GFLOPS in every case (perf_CPU.txt). CUDA0 values for kv < 196,608 are from perf_CUDA0.txt
(the script's summary parser printed only the 196,608 nb 2 line, because CUDA graph warmup lines split the others).

Notebook reading: "The stock CPU kernel is compute-bound (~17 GMAC/s: per query head, fp32, no reuse of a K/V row
across the 6 heads of a group)." Estimate for a dedicated kernel: "q8 query x q4_0 K int8 dots with 6 heads per row
load ~3 ms; V in fp32 FMA ~15 ms; 226 MB of rows at ~35 GB/s ~6.5 ms, overlapped): ~15-20 ms per layer at nb 2 =
PCIe speed. Value only as a split (CPU part of the rows, PCIe the rest): ~1.5-1.9x decode at depth, exact."

## Deviations, incidents, void runs

- First try (queue 10:29:07) ended at once: the CUDA runtime DLLs were not next to the exe ("P95 first try failed
  (CUDA runtime DLLs not next to the exe); requeued"). The script then copied the missing DLLs from bin-0046. The
  queue log shows "done" for the failed try (exit 0), so the runner did not flag it.
- P95 ran alone (no server), after P96 (queue 59zz).

## Verdict

Notebook: "stock CPU flash attention is 7-15x too slow for the host tail - gate FAIL". 192k rows, 2 queries: 278.0
ms vs the 12 ms gate (PCIe today ~19 ms). Next: P97, a standalone AVX2 microbenchmark of a dedicated kernel. "Gate
for the engine change: <= 12 ms per layer, 192k rows, nb 2, 12 threads."
Alternative named here (Cary's call): block-sparse top-k attention for the host rows (Quest-like block key summaries
in VRAM, fetch ~10-20 % of host rows per step), "decode at 250k could approach the 64k speed; needs KLD / NIAH / long
task gates; opt-in only."

## Corrections later

P97 (dedicated kernel) also failed: ~110 ms per layer at 192k rows. The CPU route was dropped. The block-sparse
alternative became the sparse host-tail work (P98-P106, issue #21).

## What it changed

No engine change. Documented in docs/8GB.md "What does not help" and docs/DEPTH.md "What did not help" (PR #20).

## Toolbox (for the next model)

- Lever: hybrid CPU/GPU attention for an offloaded KV tail (CPU computes partial softmax over RAM rows, exact merge).
- Model-specific: GQA 6 with head 256 and 4 KV heads per layer, 16 attention layers; ~24k multiply-adds per row for
  2 query tokens (K and V). The stock CPU kernel does not reuse a KV row across the 6 query heads.
- Transfers: check the arithmetic before the bandwidth. A 6-core desktop CPU does ~35 GFLOPS in this op; with GQA and
  a large head size the CPU is compute-bound long before it is memory-bound. Worth re-checking only on many-core
  CPUs or models with small heads / low GQA, or a slower link than PCIe 3.0 x16.
