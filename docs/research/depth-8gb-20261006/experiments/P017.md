## Question

Does L2 prefetch (MAX_KB=1024) combined with drafting cause the one-token answers that P013's C2 gave at 32k and 60k?

## Why

P013: "C2 at 32k and 60k generated one token on all three prompts ... P12's C2 (same N, PCT=0) produced 400 tokens at
32k. Only difference: GGML_CUDA_L2_PREFETCH_MAX_KB=1024 (prefetch on). Prefetch code cannot change values
(prefetch.global.L2 only) - P17 (2x2 drafting x prefetch, text captured) decides before anything else uses prefetch."

## Plan and gate

P013 result: "P17 (2x2 drafting x prefetch, text captured) decides before anything else uses prefetch." No numeric gate
was written; the reading is whether one-token answers follow prefetch, drafting, or neither.

## Method

2 x 2 arms, one server each, in this order: c2_pf1024, c2_pf0, b_pf1024, b_pf0. depth_text_probe.py at depth 32000:
fresh filler + two prompts ("merges overlapping intervals, with tests. Code only." and "how a heat pump works in winter,
step by step"), 200 tokens, greedy, texts, finish reason and token count saved; server logs copied.

## Results

| C2, prefetch 1024 | 01:21:48 | length / 200 / 46.0 | length / 200 / 44.0 |
| C2, PCT=0 | 01:24:11 | length / 200 / 45.8 | length / 200 / 43.8 |
| B, prefetch 1024 | 01:26:32 | length / 200 / 34.7 | length / 200 / 34.8 |
| B, PCT=0 | 01:28:52 | length / 200 / 34.4 | length / 200 / 34.4 |

All 8 requests produced 200 tokens. Texts identical across prefetch on/off for each mode. Not in the notebook (from the
json): C2 vs B, the code text is identical and the prose text differs. The C2 server log shows the fresh prompt
evaluated as 32,039 tokens at 303.72 tok/s.

## Deviations, incidents, void runs

- The B arm used N=58112, not P013's N=77568. The C2 arm matches P013 exactly.
- The probe sends a fresh 32k prompt; it does not repeat P013's quick_tps sequence. That difference turned out to be the
  cause (below).

## Verdict

"prefetch cleared; the one-token stop does not reproduce on a fresh 32k prefill." "Difference from P13: quick_tps sends
"Say hi." before each depth, so the 32k request restored the 16k prefix from the server's RAM prompt cache (P13 log:
16,524 of 32,040 tokens evaluated) and its first sampled token was end-of-turn on all three prompts. P12 and P15 ran the
same sequence without failing -> intermittent, involving prompt-cache restore of a long prefix with drafting on
(recurrent state / draft context restore). No-head B never failed."
P18 plan: "replay P13's exact quick_tps sequence (4k -> 16k -> 32k) x3 on the drafted default (tail 1, N=47360) and x3
on C2 tail 2; count one-token answers; capture texts and server logs. Any failure blocks the drafted default until
root-caused; zero in 6 replays -> recorded as unreproduced, kept under watch."

## Corrections later

- P018 reproduced the stop (tail 2, restore sequence). P054 (2026-10-09, outside this range) attributed the P018 failures
  most likely to the shared CUDA pool race (GGML_CUDA_SHARED_POOL=1, fixed by patch 0045). Both C2 arms here ran with
  the pool on and did not fail; the failure is intermittent.

## What it changed

L2 prefetch was cleared as a cause; the investigation moved to the prompt-cache restore path (P018, P021).

## Toolbox

- Method: when a failure appears in one configuration, cross the suspect factor with the mode (2 x 2) and capture texts,
  finish reasons and token counts, not only speed.
- Lesson: check what the server actually evaluated (prompt_n, cached tokens); a probe that sends a fresh prompt does not
  test a prompt-cache restore.
- Transfers: prefetch instructions cannot change values; text identity across prefetch on/off is the expected result.
