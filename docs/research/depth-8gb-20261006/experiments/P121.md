## Question

At which depth does sparse (with no threshold) beat dense on 8 GB, so that MIN_HOST can be set from data?

## Why

The 4070 asked for it after D18. Known points: P106 64k (host tail ~18k cells) sparse -16 %; P112 160k 2.15x. P121
fills 96k and 128k.

## Plan and gate

Script header: "Note: P118 found an always-on cost of FA_SPARSE inside FLASH_ATTN_EXT (+15 ms per graph at 64k). It is
in the sparse arm here too, so this crossover is for today's build; it moves lower when that routing is fixed.
Reading (declared before the run, no pass/fail): decode ratio sparse / dense at 96k and 128k, with P115 (64k
never-sparse 22.8 vs 28.7, so sparse loses there) and P112 (160k 19.6 vs 9.1). Recommend MIN_HOST = host tail at the
first depth where sparse >= 1.05x dense."

## Method

Two arms, one server each (dense 19:36, sparse0 19:57): quick_tps 96000 then 128000 (code, prose, bash, 400-token
greedy decodes), a 10 s nvidia-smi trace, and a count of sparse_mask log lines.

Reading: sparse >= 1.05x already at 96k (host tail ~61.4k). With P106 (host tail ~18k, -16 %), the crossover is between
~18k and ~61k host cells, so MIN_HOST=32768 is inside that range.

## Deviations, incidents, void runs

- The script header says "96k then 128k (extends)". The receipts show a full prefill at 128k in both arms (127,340
  tokens evaluated), not an extend. Both arms did the same, so the ratios hold.
- MIN_HOST=0 makes every op with a host tail sparse, so the P118 eligibility bug (it skips the prefetch only below
  MIN_HOST) cannot touch this run (the 2060 on #21, 00:53Z). The always-on routing cost in the header note does not
  apply to a MIN_HOST=0 arm in that reading.
- The run used the prototype env (graphs off, lookup off, f16 mask, margin 475, line 34,560); the shipped launcher
  differs. P122 repeats the crossover on product-sparse with the launcher-sparse defaults.

## Verdict

DONE. Notebook: "With P106 64k (host ~18k: -16 %): crossover between ~18k and ~61k host cells; MIN_HOST=32768 in
range. Posted on #21."

## Corrections later

P122 (product-sparse, launcher defaults, graphs on, lookup on, line 62,464 dense vs 48,640 sparse) moves the picture:
dense is much faster there (96k 24.6 vs 15.9 here), and sparse wins only 1.02x at 96k and 1.17x at 128k, because the
page-bound reserve shortens the line at every depth.

## What it changed

MIN_HOST=32768 kept as the provisional launcher default (PR #49). Posted on #21 (6158715730).

## Toolbox (for the next model)

- Method: measure the crossover at two or more depths on both sides, with the threshold off (MIN_HOST=0), then set the
  threshold in the gap.
- Pitfall: a crossover measured with a test env (short line, graphs off, lookup off) does not hold for the shipped
  launcher; repeat it on the product build.
