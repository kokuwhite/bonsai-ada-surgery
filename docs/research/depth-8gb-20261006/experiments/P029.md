## Question

Does the final drafting configuration (with f16 prefill on) give one-token answers through P013's prompt-cache restore
sequence?

## Why

P018/P021: the one-token bug appeared with tail 2 after a prompt-cache restore; tail 1 had 0 in 54 answers. f16 prefill
(P025) changes the prefill path, so the final configuration needs its own replays.

## Plan and gate

(quoted) "During the RC2 build (CPU busy: timing not read, correctness only). bin-p25, drafting config of the release
(q4 head, draft 1 / tail 1, pool, N=47360, GGML_CUDA_FA_PREFILL_F16=32768), P13's sequence (4k -> 16k -> 32k with
prompt-cache restore) x3. Gate: 0 one-token answers."

## Method

p29.sh: three replays (r1 06:35:24, r2 06:40:00, r3 06:44:15), each a fresh server and quick_tps 4k -> 16k -> 32k
(9 answers per replay).

## Deviations, incidents, void runs

r3 was cut short: "the RC2 build finished earlier than estimated and P28's first stop killed r3's server (its next
request got "connection refused"); r3's closing stop found no server, and P28's server (pid 6720, 06:46:23) was the
only one when P28 measured - no cross-contamination." In the receipt the 16k bash request ends with
"ConnectionResetError: [WinError 10054]" and the 32k requests with "[WinError 10061] ... actively refused"; r3's "min
free" line reads 7,618 MiB (no server). r3 produced 5 answers (4k x3, 16k code and prose).
"Lesson: a chain waiting on a build must also wait on any GPU job started meanwhile."

## Verdict

"final drafting config, 0 one-token answers in 23 (replay 3 partial)." Gate PASS.

## Corrections later

- P064 (2026-10-08, outside this range): with the same pool setting, fresh long prompts (60k, and 30k lookup items) gave
  one-token answers on a newer engine in 7 of 10 pool-on runs; the restore-sequence replays here did not catch it.
  Patch 0045 (poolsync) fixed the race; the preset dropped the pool until then.
- The "0 of 77" total counts all answers at 4k/16k/32k (P018 27 + P021 27 + P029 23), not 32k answers only.

## What it changed

Cleared the RC2 drafting configuration on the restore sequence; RC2 shipped with it (P028).

## Toolbox

- Method: correctness replays can run while the CPU builds (timing ignored), but every chain must wait for all GPU jobs
  before stopping servers.
- Lesson: one replay pattern (prompt-cache restore) does not cover all triggers of a race; add fresh long prompts above
  every cap (f16 cap here) to the correctness set.
