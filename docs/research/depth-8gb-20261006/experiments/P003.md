## Question

Does a higher GDDR6 clock raise decode speed on this card, and is the output still exact?

## Why

The handoff assumed decode scales with memory bandwidth. P002 noted that under CUDA load the card sits in the P2 power
state at 6,801 MHz, not 7,000.

## Plan and gate

Slots applied by scheduled tasks BonsaiAB_P1..P5 (admin, no prompt). Arm order: stock, +250, +500, +750, +1000, stock
again (drift check). memclock_probe.py: 4k filler (in VRAM), 2 prompts x 400 tok greedy x 2 reps, memory clock sampled
under load. Gates per arm, written before the run (quoted):
- "identity: every output text byte-identical to the stock arm's (greedy; any difference = memory errors -> arm fails,
  and every higher offset is skipped);"
- "speed: keep the highest offset whose mean decode beats the previous arm by more than the stock-vs-stock-again
  spread (GDDR6 error retry shows as flat or falling tok/s, not a crash);"
- "the clock actually moved under load (nvidia-smi clocks.mem max > the previous arm's)."
"Afterwards: apply slot 5 (stock) unless the winner is confirmed by a 10-minute soak in a later entry."

## Method

memclock_probe.py warms a ~4,000-token filler with "Say hi.", then sends two prompts (code: ISO 8601 duration parser
with tests; prose: how a refrigerator works, ~400 words), 400 tokens, temperature 0, thinking off, 2 reps. A thread
samples nvidia-smi `clocks.mem, clocks.gr, temperature.gpu, power.draw` every second (44-50 samples per arm). The
sweep script applies a slot, waits 4 s, runs the probe, compares texts with the stock arm, and stops at the first
mismatch.

Gates: identity PASS at every offset (+1000 included; "IDENTICAL" for every arm). Clock moved PASS (offsets apply 1:1 in

the stock-vs-stock drift of 1.68 tok/s (4.8%).

## Deviations, incidents, void runs

None in the run. The design has a weakness that the result shows: the arms run in rising order while the card heats, so
heat drift and offset are confounded (stock 36.73 to stock-again 35.05).

## Verdict

The notebook concluded: "PTQ1_0 decode on Turing is core-bound, not bandwidth-bound; the drift tracks the core clock
falling from 1875 to 1650 as the GPU passes its 81 C target. Power touched the 175 W limit (max slider 215 W)." Card
left at stock (slot 5). "Handoff's 'scale by bandwidth' assumption does not hold here."

## Corrections later

- P038 (2026-10-07, outside this range): "The 2026-10-06 memclock sweep ran on the pre-#325 engine at ~36 tok/s with 5%
  stock-to-stock drift: inconclusive." On the current engine with llama-bench tg256, memory +500 gave +4.2% and +1000
  gave +7.7% (gate PASS). Title of that entry: "the old 'memory OC does nothing' is void". docs/8GB.md "Not used: memory
  overclock" was marked wrong.
- 2026-10-07 incident (outside this range): memory +1500 crashed the PC (bugcheck 0x20001); +1250 later GPU-faulted
  under load. The cap is +1000.
- So the P003 conclusion "memory clock does not limit decode" is wrong for the planar-PT engine. On the SOA_ISUM engine
  of this run the speed gain was inside the heat drift.

## What it changed

At the time: the card stayed at stock and the focus moved to core clock (P004) and VRAM positions. Later: P038/P042
re-opened memory overclocking as an opt-in (+1000) for the owner.

## Toolbox

- Method: Afterburner profile slots applied by scheduled tasks (no UAC prompt), probe per slot, byte-identity of greedy
  text as the error detector. It transfers to any NVIDIA card on Windows.
- Lesson: alternate arms (stock / OC / stock / OC) or measure with a short benchmark (llama-bench) so that heat drift
  does not hide a 5-8% effect. A rising sweep on a heating card confounds the two.
- Lesson: a "bound by X" conclusion is engine-specific. After a kernel change (#325 here) re-measure it.
- Card-specific: GDDR6 on this 2060 SUPER is safe to +1000 (later receipts), crashes at +1500.
