## Question

Does a clean release build (only the Turing fix and the shared pool on the product branch, all bundle architectures)
reproduce the dev-build numbers in both 8 GB modes, with no one-token answers and no prefill cliff?

## Why

P012-P015 set the drafting mode on bin-p12 (a dev build with #314 and #209). P014c set the long mode's N away from the
cliff. A release needs the product engine and the repo's own head tooling.

## Plan and gate

"Engine: vendor/prism-pool = bonsai-q8-product (c8b8993) + Turing fix (bc3e5aa) + Mirai shared pool (b7c11567a); no #314,
no #209. Build sm_75/86/89 + compute_89 PTX like bundle-20260927 -> bin-rc. On this card: drafting mode (q4 head,
draft 1 / tail 1, pool, N=47360) and long-context mode (no head, N=67840), full sweep 4k/16k/32k/60k each, run twice;
one 10-minute soak of the long-context mode at 67,840 (block design). Gates: within 2% of the bin-p12 numbers
(drafting: minus the ~1.5% prefetch gain); no one-token answers; no prefill cliff in either mode; free >= 200 MiB.
Repo branch 8gb-rig (local, not pushed): display detection 4042bb3, Q4 head tooling, docs/8GB.md draft - numbers in the
doc replaced with P20's before Cary decides to publish."

## Method

p20.sh: (1) build bin-rc; (2) run the repo's make_mtp_q4head.ps1 end to end on a copy of the mtp file in models\rc-test,
strip proof, byte compare with the night's q4-head file; (3) wait for P021 to finish (P021 used the GPU during the
build); (4) draft_r1, long_r1, draft_r2, long_r2 through run_arm.sh at 4k/16k/32k/60k; count "(1 tok)" lines.

## Deviations, incidents, void runs

- The planned 10-minute soak of the long mode at 67,840 (block design) was not run: p20.sh has no soak step and the
  result does not mention it.
- "one-token answers 0/24": the four runs hold 48 answers (4 runs x 4 depths x 3 prompts); the script's count over all
  four files is 0. The 24 matches the drafting runs only.
- "free" at the end of the drafting runs was 184 MiB (below the 200 gate value at load); the gate was written for load.

## Verdict

"release candidate confirmed on this card; decode beats the floor, prefill does not at depth." The result attributed
the prefill gap to "attention over the deep cache, his f16-converted FA vs our in-place q4_0 read on Turing". "Prefill at
depth is the open item against Cary's floor."

## Corrections later

- P022 noticed long-mode 32k prefill 300 (bin-p22) and 302 (bin-p12, P14c) vs 271 here; P023 showed it is the request
  sequence (4k -> 32k evaluates 28,512 tokens; P020's 16k -> 32k evaluates 16,524), not a build difference.
- P025-P028: f16 prefill and ub 1024 changed both modes; RC2 (P028) replaced bin-rc.
- P064 (outside this range): the shared pool in this drafting mode later caused one-token answers on fresh long prompts.

## What it changed

The 8 GB release-candidate configuration (engine prism-pool, drafting N=47,360 and long N=67,840) and verified repo
tooling (build/make_mtp_q4head.ps1).

## Toolbox

- Method: a release candidate is the product branch plus only the needed commits, built for all shipped architectures,
  then measured twice in each mode against the dev numbers (within 2%), with one-token counts and free VRAM.
- Method: verify a model-transform script end to end on a copy and byte-compare with the known-good output.
- Transfers: keep dev-only commits (prefetch, fusions) out of a release until they pass on every target card.
