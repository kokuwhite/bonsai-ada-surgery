## Question

Can a CPU kernel written for this layout (int8 K dots, each row loaded once for the 6 query heads of a group) compute
the host-tail attention within 12 ms per layer at 192k rows and 2 queries?

## Why

P95: the stock CPU flash attention needs 278.0 ms per layer (compute-bound, no reuse of a KV row across the 6 heads).
The P95 estimate for a dedicated kernel was ~15-20 ms per layer, "value only as a split".

## Plan and gate

From the P95 result entry: "Next: P97, a standalone AVX2 microbenchmark of that kernel before any engine work. Gate
for the engine change: <= 12 ms per layer, 192k rows, nb 2, 12 threads." No separate plan entry.

## Method

cpuattn_bench.cpp (header): one layer of R cells; each cell holds K and V rows of 4 KV heads x 256 dims in q4_0
(18-byte blocks of 32): 1,152 B per cell. Queries: nb tokens x 24 heads (GQA 6). K: q8 query x q4_0 K int8 dots with
`_mm256_maddubs_epi16`, one unpack per block for 6 heads x nb. V: dequant once per block, fp32 FMA into 6 x nb
accumulators. Tiled online softmax (32 rows per tile); per thread a partial (max, sum, unnormalized V) merged at the
end (the form a GPU merge would take). Also times a plain read pass of the rows.

## Results

Notebook: "16,384 rows nb 2: 9.5 ms per layer -> ~110 ms at 192k rows (PCIe today ~19 ms). Read pass 23 GB/s. The
limit is arithmetic: 2 tokens x 24 heads x 1024 dims x K+V = ~24k MAC per row, ~4.7 G per layer at 192k; a 6-core
Ryzen 5 2600 cannot do that in 19 ms. Best case as a split: ~1.3-1.5x, with every core busy during decode. Not worth
the engine change."

## Deviations, incidents, void runs

- No receipt file was saved for the benchmark output; only the notebook line holds the numbers (9.5 ms at 16,384
  rows, read pass 23 GB/s). The 192k value (~110 ms) is an extrapolation from 16,384 rows, not a run at 196,608.

## Verdict

Gate FAIL: ~110 ms per layer vs <= 12 ms. "CPU attention route dropped."

## Corrections later

None. docs/8GB.md and docs/DEPTH.md carry "~110 ms per layer for 192k rows on a 6-core CPU vs ~19 ms over PCIe".

## What it changed

Route dropped. Notebook list of the depth decode levers left: "(1) approximate block-sparse attention for the host
rows (Cary's call); (2) more verified tokens per host read (tail 2 = +17 % at 200k, -10 % at 64k; lookup for
copy-heavy work); (3) fewer bits per host row (custom KV type: ~1.3-1.5x, quality cost)." These became P98-P106
(sparse), P80b/c (tail 2) and P100 / P108 (3-bit KV).

## Toolbox (for the next model)

- Lever: CPU attention over an offloaded KV tail. Measured dead on a 6-core CPU for this shape.
- Model-specific: ~24k MAC per KV row for 2 query tokens (24 query heads x 1,024 dims for K and V); head 256 and GQA 6
  make the row work large.
- Transfers: estimate MACs per row x rows / CPU throughput before writing a kernel. The read pass (23 GB/s) was not
  the limit; arithmetic was. Recheck only with far more cores, AMX/AVX-512 int8, or much smaller heads.
