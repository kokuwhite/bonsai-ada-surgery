## Question

How much system memory (commit) does the 8 GB preset at a 131k window take during sequential long thinking
requests, which component takes it, and which launcher defaults keep a 16 GB machine alive?

## Why

Issue #16 (howdya: RTX 3060 Ti 8 GB, 16 GB RAM): 131k tiered (N 42,496), thinking on, 7 sequential requests: 3 HTTP
500 ("bad allocation"), then the process died. The server log showed "prompt cache limit reduced to 757 MiB" and
entries of 459-728 MiB evicted each request. The notebook's estimate of the RAM bill at 131k on 16 GB: pinned KV tail
~1.5 GB; context checkpoints up to 32 per slot x ~170 MiB (~5.4 GB; the 8 GB preset adds them every 8,192 tokens
inside messages, patch 0046); prompt cache (default 8192 MiB limit). bad_alloc = commit limit.

Issue #16 split (4070 comment, same day): the 2060 rig owns the launcher RAM-budget PR (one block for all presets);
the 4070 measures the 12 GB recipe (262k q8_0 tail ~4.6 GB pinned) and adds its numbers to that PR. Server facts from
the 4070: "cache size limit reduced" is written after a bad_alloc (limit -> 40 %); a prompt-cache entry holds a copy
of the slot checkpoints (459-728 MiB = 3-4 checkpoints), so checkpoints sit in RAM twice.

P90d)."

## Method

- One server per arm (stop.ps1, Afterburner slot 3 then 5, serve.ps1 with the arm's launcher and variables, wait for
  /health). The launcher's `window`, `kv` and `ram` lines are saved.
- ram_probe.py: 7 sequential chat requests (7 fixed coding/maths prompts, thinking on by the launcher defaults,
  max_tokens 4096, temperature 0.6). A thread samples llama-server PrivateMemorySize64 (commit), WorkingSet64, and
  the OS FreeVirtualMemory (free commit) and FreePhysicalMemory every 5 s through PowerShell.
- From P90b on: `--prefix-words 6000`: each request gets a different random prefix of 6,000 "word+number" tokens
  ("Background notes (ignore unless needed)"), so every request has a long, new prompt (prompt cache entries and
  checkpoints are created as in a long agent session).
- Server err.log grep for "cache size limit", "removing oldest", "bad alloc", "exceeds cache size", checkpoint lines.
- Ballast (P90c, P90d, P90e b16): ballast.py commits G GiB with VirtualAlloc(MEM_RESERVE | MEM_COMMIT) and never
  touches the pages (no physical RAM used), G = (free commit - 13,312 MiB) / 1024. Killed after the arm.
- Health check after the 7 requests (P90c on).
- Arms: P90 / P90b default, capped, budget; P90c budget (v1) with ballast; P90d budget (v2) with ballast; P90e t32
  (no ballast, RAM tiers) and b16 (ballast + BONSAI_RAM_GB=16).

### Shipped formula (start-server.ps1 on main, from these runs)

48 GB or more: server defaults (8192 MiB cache, 32 checkpoints). 24-47 GB: cache 4096 MiB, 32 checkpoints. Under 24
GB: budget = free commit - server VRAM - pinned tail - 2048 MiB; checkpoints = 40 % of the budget / 170 MiB (4 to
32); cache = half of what the checkpoints leave, 0 below 1536 MiB. Check against the receipts: P90d 13,434 - 7,477 -
1,274 - 2,048 = 2,635 MiB -> 6 checkpoints, cache 807 -> 0 (as logged). v1 (P90c) gave the cache 60 % (1,580 MiB).

## Deviations, incidents, void runs

- **P90 VOID for memory.** ram_probe.py's sampler thread crashed at once in every arm: `OSError: [WinError 6] The
  handle is invalid` from subprocess.run (no stdin handle under the queue task). The .jsonl files hold only the 7
  request rows; no `mem` rows. Fix: `stdin=subprocess.DEVNULL` in the sampler (the version in scripts/ram_probe.py).
  The prompts were also short (39-106 tokens), so the run could not show prompt-cache growth. P90b reran it with the
  fix and `--prefix-words 6000`. The notebook has no P90 result entry; only P90b's.
- **Prompt size in the notebook vs the receipts.** The notebook calls the P90b-P90e prompts "~8k-token prompts" and
  says "one 8k-prompt entry is ~1.3 GB". The receipts show prompt_tokens 24,387-24,455 for every request (6,000
  random "word123" tokens take ~4 tokens each, not the ~1.3 the script help assumed). The 1.3 GB entry size is
  measured; it belongs to a ~24.4k-token prompt.
- Completion tokens above max_tokens 4096 (e.g. 5,769, 5,957): the receipts show them; the notebook does not discuss
  them.
- P90c budget launcher chose cache 1580 MiB: the cache stored a new 1.3 GB entry before it dropped the oldest, and
  free commit fell to 682 MiB. Gate "min free commit > 0" was met, but the notebook treated the margin as too thin
  and changed the formula (v2).
- P90e: the page file grew between runs (free commit 26.4 -> 53.4 GB), so the b16 ballast was 39 GiB instead of 12.

## Verdict

- P90b: the defaults take the server from 9.6 to 18.3 GB of commit in 7 requests (+8.7 GB): a 16 GB machine cannot
  hold that. Confirms #16.
- P90c: gates met (small cache, 7/7, alive, min free commit 682 MiB > 0); margin too thin -> formula v2.
- P90d: "PASS" (notebook): 7/7, alive, peak 10.5 GB, min free commit 1,980 MiB >= 1.5 GB.
- P90e: tiers work: 32 GB tier peak 14.4 GB (vs 18.3 with defaults); 16 GB tier 7/7, alive, min free commit 1.39 GB.

## Toolbox (for the next model)

- Lever: size the server's prompt cache and context-checkpoint count from the machine's free commit, not from a fixed
  default. Measure commit (private bytes), not working set: on Windows (WDDM) a process's commit also grows with its
  VRAM allocations, and bad_alloc comes from the commit limit.
- Method: simulate a smaller machine with an untouched-commit ballast (VirtualAlloc commit without touching pages);
  it takes free commit but no physical RAM, so one 32 GB rig can test the 16 GB case without swapping.
- Model-specific: the checkpoint size (~170 MiB each) is this model's recurrent (gated-delta-net) state for 48 GDN
  layers; a prompt-cache entry holds the prompt's K/V plus copies of its checkpoints (~1.3 GB for a ~24.4k-token
  prompt with q4_0 K/V). A pure-attention model has no checkpoints, so only the cache part applies.
- Transfers: the cache stores a new entry before it evicts the oldest, so the free-commit reserve must hold two
  entries; a cache limit below one entry only adds churn (set it to 0 instead). Count tokens from the server's
  usage field, not from a words-to-tokens guess.
