## Question

Does lookup drafting still pay at depth 120,000 (past the VRAM line), and does the server stay healthy there?

## Why

Overnight backlog item 2: "lookup on/off at depth 120000 (quote + edit + plain), drafting preset, bin-lookup."

## Plan and gate (as frozen before the result)

"P50: drafting preset, bin-lookup, lookup_ab.py at depth 120000, lookup 0 then 1. Reading: quote/edit/plain tok/s at
the deep end, min free VRAM, server alive. Gate for "on at depth": quote and edit faster, plain within 2 %, no death."

## Method

Two servers (lookup 0, then 1); lookup_ab.py with a ~120k-token filler in front of every request; free VRAM every 2 s.

## Deviations, incidents, void runs

1. First attempt (jobrun7, 01:44): failed at once, same lookup_ab.py import bug as P49 (fixed).
2. quote csv.py returned 1 token in both arms. Notebook (P59 plan): "Also seen: quote csv.py at 120k returned 1 token
   in both arms (P50) - a one-token answer; P54 investigates."
3. Wall time per request 746-866 s: every request whose prompt changes inside the long first message re-prefills the
   whole ~120k context. Only the short plain tails reuse (38-40 s). This motivated P59.

## Verdict

Not written in the notebook as a P50 result. By the frozen gate: quote faster (x3.4) and edit faster (+30 %), plain
not slower (+2.8 %), no death -> PASS for "lookup on at depth". The one-token answer is a separate bug (both arms).

## Corrections later

- P61 (2026-10-08) saw more 1-token answers on fresh long prompts; P64 found the cause: the shared CUDA pool
  (`GGML_CUDA_SHARED_POOL=1`, set by the 8 GB preset then). Hotfix PR #10 (pool off); patch 0045 (poolsync) fixed the
  engine race (P68/P69). P50 ran with the pool on.
- P71 / PR #11 (patch 0046 `--checkpoint-every-nt`) later cut the re-prefill: 64k wall per request after the first
  ~60 s vs 227 s (P73).

## What it changed

docs/8GB.md (PR #12): "Lookup file rewrites: 69 tok/s at 64k, 42 at 120k." Started P59 (mid-message checkpoints).

## Toolbox (for the next model)

- Transfers: at depth past the VRAM line, lookup still multiplies quote-type decode (x3.4 here), because the verify
  step is PCIe-bound and extra columns are cheap. The wall time is dominated by re-prefill, not decode, when the prompt
  changes inside one long message: fix the cache/checkpoint path before you tune decode at depth.
