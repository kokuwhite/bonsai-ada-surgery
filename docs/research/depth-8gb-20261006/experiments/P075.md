## Question

Can the 8 GB card serve a 262k window with the full current stack (patch 0046, lookup on, no pool, checkpoints
every 8192), and at what cost per depth?

## Why

Cary asked about 262k on 8 GB. "The window is set by system RAM (q4_0 host part ~4.7 GB at 262k); P30 loaded it
(43.1 at 4k)."

## Plan and gate

Notebook: "BONSAI_CTX=262144, drafting preset. quick_tps 4k / 64k / 128k / 192k / 250k (each extends); then
lookup_ab.py at 250000 (first request full prefill, the rest restore checkpoints). Record: positions in VRAM, free
VRAM at load / min, prefill and decode per depth, lookup tok/s at 250k, wall per request, RAM, one-token count.
Gates (to recommend 262k on 8 GB): server stays up; 0 one-token; min free >= 60 MiB; decode at 4k within 3 % of the
131k preset (51.7). Deep numbers are reading only."

## Method

Sweep: one server, quick_tps at 4000, 64000, 128000, 192000, 250000 (each step extends with ~58-64k new code tokens).
Lookup arm: a new server, lookup_ab.py at depth 250000 with nvidia-smi free VRAM and the server working set every 20 s.

Partial result (notebook): "VRAM positions 41,472 (131k preset: 50,176). Decode 4k 51.9 (= 131k), 64k 24.1 (131k: 30.7,
-21 %), 128k 9.9 (131k at 126k: 14.2, -30 %), 192k 6.9. The launcher reserves the tier staging buffer, (ctx - N) x
CellBytes / 16 of VRAM, so the VRAM line moves down 8,738 positions per extra 131k of window."
Lookup at 250000: the first request (full ~250k prefill at ~65 tok/s) passed the 1800 s client timeout (ab.txt:
TimeoutError). No result.
Memory trace (ab.mem.txt, 89 samples, 10:02:49 to 10:32:46): free VRAM 201 -> 125 -> 65 -> 21 MiB in the first
62 s, then below zero (4194275-4194301) for 85 of 89 samples. Server working set peaked at 7473 MiB, then fell to
~550-1050 MiB while the prefill ran.
Notebook: "The driver puts the excess in shared system memory. This is a probable part of the deep-end loss, in
addition to the smaller VRAM line."

## Deviations, incidents, void runs

- Lookup arm void: client timeout 1800 s too short for a cold 250k prefill on PCIe 3.0. Notebook: "Use 5400 s for deep
  runs." (lookup_ab.py now uses 5400 s.)
- Build fault in the same window (not this experiment): "tune build at 09:57 crashed in cicc (ACCESS_VIOLATION,
  fattn instance, during P75 RAM load) but build.bat returned 0; P78 ran on a bin with no exe and failed in 1 min."
  See P078 and the events file.

## Verdict

Notebook: "Gates: server up - yes; 0 one-token - yes (sweep); min free >= 60 MiB - FAIL; 4k decode within 3 % of 131k
- pass (51.9). Decision: do not recommend 262k with today's preset. P77 (staging off, N = 54,784) is the next test.
Its min-free gate now also needs a memory trace through a deep prefill (>= 128k), not only at load."

## Corrections later

- P77 found the second cause of the over-commit: the f16 KQ mask is n_ctx x ubatch x 2 B and the launcher FixedMiB
  did not scale it with the window (128 MiB more at 262k).
- P81 (partial staging, mask-aware launcher): 262k without over-commit; D vs P75: 64k 26.9 vs 24.1 (+12 %), 128k 12.3
  vs 9.9 (+24 %).
- P84 / P85: packed mask + pool + partial staging make 262k the 8 GB default (64k 37.5-37.8, 128k 14.1-14.2).

## What it changed

262k not recommended with the then-current preset. Memory traces through deep prefills became a standard gate
(every later arm has a <arm>.mem.txt and a "trace min free" line, wrap corrected).

## Toolbox

- Method: trace free VRAM through the whole run, not only at load. On Windows (WDDM) an over-commit does not crash: the
  driver spills to shared system memory and the run just gets slower. nvidia-smi then reports ~4194xxx MiB (wrap).
- Lever cost found: a staging buffer sized by (window - N) takes VRAM from the KV line as the window grows.
- Model-specific: q4_0 KV cell = 18,432 B at 16 attention layers x 4 KV heads x 256 dims (K+V); 262k host part
  ~4.7 GB.
- Transfers: any tiered KV cache with per-window VRAM structures (staging, masks) must count them per window size.
