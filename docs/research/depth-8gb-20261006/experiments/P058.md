## Question

main b8ba790 (Ada, #330 data): lookup verify batches lose 9-10 % on file rewrites with `GGML_CUDA_FA_PREFILL_F16`. Does
the same happen on Turing?

## Why

"Our drafting preset sets it to 32768; the f16 path takes Q->ne[1] > 8, and a lookup verify batch is 33 columns, so
each verify step may convert the cache to f16."

## Plan and gate (as frozen before the result)

"A/B: drafting preset with lookup, bin-lookup, lookup_ab.py at depth 0 and 32000, GGML_CUDA_FA_PREFILL_F16=32768
(preset) vs 0. Gate: if 0 is faster on quote/edit by > 3 % at either depth -> change patch 0038's threshold to
prefill-sized batches only (e.g. Q->ne[1] > 64), measure prefill unchanged, and send the fix to the patch stack and
PrismML #330."

## Toolbox (for the next model)

A prefill-only switch whose threshold is "more than 8 queries" also catches multi-token verify batches (lookup: 33
columns). Check every batch shape your server sends before you set such a threshold.
