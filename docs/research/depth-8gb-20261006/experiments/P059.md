## Question

Can a checkpoint every N prompt tokens inside one long message stop the full re-prefill when a prompt changes deep in
that message?

## Why

"Code read (agent): this hybrid model checkpoints only at user-message starts and 4 / 4+n_ubatch tokens before the
prompt end (server-context.cpp:3578 skips mid-message checkpoints; upstream removed --checkpoint-every-nb, #20087, and
has the same rule today). A prompt that diverges inside one long message re-prefills everything: P50 120k requests
760-866 s each; only tails < 516 tokens reuse (39-40 s)."

## Plan and gate (as frozen before the result)

"Patch (branch patch-ckpt-every-nt on the fork, off by default): --checkpoint-every-nt N / LLAMA_ARG_CHECKPOINT_EVERY_NT
keeps a batch-start checkpoint N tokens past the last. Test: build sm_75 (bin-ckpt); drafting preset with lookup;
lookup_ab.py at 64000 with N=8192 vs 0. Gates: wall time per request after the first drops by > 50 % for quote /
plain-code items; same text hashes; decode within 2 %; host RAM and free VRAM recorded. Pass -> patch to the stack
(PR) and offer to PrismML / upstream with the receipt."

## Method

Build; then two servers (N=8192 first, then N=0), each running lookup_ab.py at 64k; every 5 s: free VRAM and the
server's working set.

## Toolbox (for the next model)

- Lever: periodic recurrent-state checkpoints inside one long message for hybrid (GDN + attention) models. Reuse at
  64k cut the wall per request from ~280 s to ~50 s.
- Model-specific: each checkpoint of the recurrent state is ~150 MiB of host RAM (working set +498 MiB here).
- Transfers: when a correct-looking feature gives wrong text, check what else in the config was unsafe at the time
  (here a shared CUDA pool race) before you mark the feature broken. Identical hashes across different prompts mean
  a corrupted state, not rounding.
