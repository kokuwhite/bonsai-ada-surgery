## Question

Does the PR #19 launcher, as users get it (chunk on for 8 GB), keep decode, VRAM, one-token and text behaviour of
the shipped 262k preset (P85)?

## Why

P89 / P89b / P89c showed that chunked prefill attention (GGML_CUDA_FA_CHUNK=32768) is exact up to rounding (PPL equal)
and faster at depth. PR #19 turns it on in the 8 GB launcher. Before the bundle, the launcher change itself needs a
check on the 2060 (P85 was the reference run of the 262k launcher).

## Plan and gate

Notebook: "P91 (plan, queue 57): PR #19 launcher as users get it (start-server-chunktest.ps1 = branch fa-chunk-8gb +
BONSAI_BIN, bin-chunk): sweep 4k-128k, fresh 60k x2, lookup_ab d0 + d64k. Gates: the 8gb line says "deeper in chunks
of 32768"; decode within 2 % of P85 (N permitting); 0 one-token; trace min >= 60 MiB; d0 texts = P85 (11/11; d0 is
below 32k so the chunk path is not used there)."

## Method

- run_arm.sh: one server, quick_tps.py 4000 -> 32000 -> 64000 -> 96000 -> 128000 (each depth extends the prompt;
  code / prose / bash prompts, 400-token greedy decodes; prefill = code prompt and 512-token prose / bash follow-ups).
  nvidia-smi free VRAM every 10 s (trace).
- Two fresh servers with one 60k prompt each (fresh60k_r1, r2).
- One server: lookup_ab.py at depth 0 and depth 64000 (11 items each: 4 quote, 3 plain, 4 edit; greedy, thinking
  off), text sha per item.

## Deviations, incidents, void runs

- Decode at 32k is +15 % against P85 (52.7 vs 45.8) and 64k is -4 % (36.0 vs 37.5); the gate said "within 2 %
  (N permitting)". The line differs (58,112 here; P85's run had 58,880 in its launcher line). The notebook did not
  evaluate this gate in a result entry.
- The notebook has no P91 result entry. P91 appears in "Posted P91/P92 (d0 plain texts change with the switch on
  although no op should chunk at d0); P93 investigating before the bundle" and in the P93 result ("P91 = P92 = P93
  (Oct 10)").

## Verdict

Launcher line PASS ("deeper in chunks of 32768"); 0 one-token PASS; trace min 111 / 139 / 105 MiB >= 60 PASS.
Depth-0 texts 8/11 against P85: gate not met. This started P92 / P93 / P94.

## Corrections later

- P92: bin-chunk with GGML_CUDA_FA_CHUNK=0 gives the same depth-0 texts as bin-pmask (11/11).
- P93: chunk off / on / off / on with this launcher: 11/11 identical in all four. "Cross-run: P85 = P88 (Oct 9);
  P91 = P92 = P93 (Oct 10)". Not the engine, not the switch.
- P94: the plain items change with the request history inside one server. So the P91 depth-0 gap is a comparison
  across days and histories, not a chunk effect.
- P96 (bundle-20261010) gave exactly the P91 texts (22/22).

## What it changed

Nothing by itself; with P92 / P93 it cleared PR #19 for the bundle ("Posted on #19: bundle can go"). Chunk on for
8 GB shipped in bundle-20261010.

## Toolbox (for the next model)

- Method: a launcher PR gets a "as users get it" run: the branch launcher, the candidate binary, the standard sweep,
  fresh long prompts and the text A/B.
- Lesson (from P91-P94): compare texts only between arms run in the same session window with the same request
  history. Greedy text on near-tie items is not stable across days.
- Model-specific: the near-tie plain items (code / prose / bash prompts) are the ones that move; quote and edit items
  (copying from context) were stable at depth 0.
