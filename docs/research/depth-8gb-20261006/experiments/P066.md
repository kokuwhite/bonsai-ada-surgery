## Question

With the preset fix of PR #10 (no shared pool), are fresh long prompts correct, is free VRAM safe, and is prefill
unchanged?

## Why

P64: the shared pool causes the 1-token answers. PR #10 removes it from the 8 GB preset.

## Plan and gate

Notebook: "P66 (plan, after P65): hotfix launcher copy (start-server-hotfix.ps1), bin-tier, drafting preset + lookup:
fresh 30k, 60k and 120k quick_tps; lookup_ab.py at 30000; per arm free VRAM at load / min and prefill. Gates: 0
one-token answers; min free >= 60 MiB; prefill at 60k within 5 % of P61 (255), no cliff."

## Method

Three servers (run_arm.sh), one fresh quick_tps each at 30000, 60000, 120000. Then one server with lookup_ab.py at
30000, with nvidia-smi free VRAM sampled every 2 s.

## Deviations, incidents, void runs

- The plan said "drafting preset + lookup"; the hotfix branch has no PR #9, so lookup was off. Not a fault for the
  gates (the bug did not need lookup, P64).
- Server used 7380 MiB with the hotfix (same in all three arms).

## Verdict

All gates pass: 0 one-token (9 quick_tps + 11 lookup_ab), min free 133-145 MiB (>= 60), 60k prefill 253.7 vs 255
(-0.5 %, within 5 %), no cliff to 120k.

## Corrections later

None. PR #9 merged later (lookup on + no shared pool on main).

## What it changed

PR #10 ready to merge. The 8 GB preset runs without the shared pool until patch 0045 engines (P83 / PR #13).

## Toolbox

- Method: a hotfix verify = the failing repro (fresh long prompt) at three depths plus the lookup item set, with a
  VRAM trace. Gate on correctness first, then on margin and speed.
- Transfers: turning a memory-saving feature off costs VRAM (here +62 MiB fixed cost = fewer KV cells in VRAM).
