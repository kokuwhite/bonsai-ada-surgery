## Question

Can the long-context mode (no MTP head) serve the full trained window of 262,144 tokens on this card, and what does
it cost in positions in VRAM, decode and prefill?

## Why

Cary asked: "can we not get higher?" P28 had verified RC2 with a 131k window. Long mode at 131k used N = 53,248
positions in VRAM (P27/P28).

## Plan and gate (as frozen before the result)

Notebook text: "Long mode on bin-rc2 with BONSAI_CTX=262144: staging doubles (+144 MiB), so N = 53248 - 8,738 ->
44,288 (same free margin as P28's long mode). Host tail (262144 - 44288) x 18,432 B = 3.8 GB pinned (32 GB RAM).
ub 1024, f16 prefill cap 65536. Sweep 4k / 64k / 128k / 200k / 250k (each extends the previous prompt; ~30+ min of
prefill). Gates: loads with free >= 200 MiB; every depth answers (no one-token); record decode and prefill per depth."

## Method

One server through the launcher (run_arm.sh), then quick_tps.py at 4k (three greedy prompts, 400 tokens each,
thinking off: code, prose, bash). The plan had more depths (64k, 128k, 200k, 250k). They did not run.

## Results

Load: used 7,819 MiB, server 7,450 MiB, free 188 MiB.

| prompt | depth | evaluated tokens | prefill tok/s | TTFT s | decode tok/s |
| --- | --- | --- | --- | --- | --- |
| code | 4000 | 4,048 | 243.7 | 16.61 | 43.1 |
| prose | 4000 | 1,024 | 231.6 | 4.42 | 43.1 |
| bash | 4000 | 1,028 | 235.2 | 4.37 | 43.0 |
| mean decode | | | | | 43.1 |

For comparison, P28 long mode at 131k (same engine, N=53,248, ub 1024): decode 43.7, prefill 432.6 at 4k.
At 262k the 4k prefill was 243.7 tok/s (-44 %).

## Verdict

Not completed. The notebook does not grade the load gate. The receipt shows free 188 MiB at load, which is below the
frozen gate (free >= 200 MiB): the load gate FAILS as written. Only one depth answered (4k, no one-token answer).
Notebook close: "262k parked with its one data point (loads; 43.1 tok/s decode at 4k; ub 1024 mask 512 MiB too costly
at 262k)." Cary: "113k is fine as long as its good, consistent quality". That sent the work to quality (P31).

## Corrections later

- 2026-10-09 P75 measured 262k again on the full current stack (bin-0046, drafting preset, lookup on, no shared pool,
  checkpoints every 8192): 41,472 positions in VRAM (131k preset: 50,176), decode 4k 51.9, 64k 24.1, 128k 9.9,
  192k 6.9. The notebook found that the cost is the tier staging buffer ((ctx - N) x CellBytes / 16 of VRAM), which
  moves the VRAM line down 8,738 positions per extra 131k of window. P77 and later P85 followed (other range).

## What it changed

Nothing shipped. The 131k window stayed the 8 GB default at that time.

## Toolbox (for the next model)

- Lever: window size vs positions in VRAM on a tiered KV cache. The host tail costs pinned RAM ((ctx - N) x cell
  bytes) and a VRAM staging buffer that grows with the window.
- Model-specific: 18,432 B per q4_0 cell (16 attention layers x 4 KV heads x 256 dims, K and V); 262,144 trained max.
- Transfers: on any 8 GB card, a larger window is not free even if it lives in system RAM. Measure the staging and
  mask buffers at the target window before you promise a window. Check the free-VRAM gate on the receipt, not from
  memory.
