## Question

Does MIN_HOST=32768 keep 64k dense (no sparse cost) and 160k sparse (the gain), and what is the clean 160k sparse
speed without OP_TIMING?

## Why

P106: sparse cost ~16 % at 64k (34.5 dense vs 29.0 sparse; host tail ~18k cells) and gave 1.9x at 160k (host tail
~114k cells). A shippable form needs a depth threshold. The 4070 added it in 3299a0b4b. P111 measured speeds with
OP_TIMING on.

## Plan and gate

Script header: "N = 32768: 64k stays dense, 160k and deeper go sparse. Same env as P111 (margin 475, lookup off, f16
mask, graphs off, no OP_TIMING). Arms, one server each, 64k -> 160k: dense, sparse + MIN_HOST=32768. Gate (declared
here, before the run): 64k sparse+threshold decode within 2 % of dense; 160k >= 1.7x dense; 0 one-token; trace min
free > 0 MiB in both arms. Runs after P111; if P111 failed its free-VRAM gate, read with care." (P111 passed it.)

## Method

Per arm: an nvidia-smi trace (used, free) every 10 s; run_arm.sh with quick_tps 64000 then 160000 on one server (the
160k step extends the 64k prompt: 95,593 new tokens); trace min free with the wrap correction. The sparse engage
lines (ggml_cuda_fa_sparse_mask, WARN level) are read from the server log.

## Deviations, incidents, void runs

- None in the run. Reading note: the dense arm here runs at margin 475 (line 34,560). P106's dense numbers are at
  margin 225 (line 46,592), so dense 64k 28.8 here vs 34.5 in P106 is the margin's cost, not run-to-run noise.

## Verdict

Partial. Notebook: "The threshold is respected ... So FA_SPARSE costs ~20 % per op even with no sparse op (candidates:
85d949f5e MMA tile map for sparse-mask ops, a per-op host read, the mask copy) - likely most of P106's -16 %. The
margin also costs: line 46,592 (225) -> 34,560 (475); dense 64k 34.5 (P106) -> 28.8."

- Clean 160k sparse speed: 19.6 vs 9.1 dense (2.15x). Follow-up prefill equal to dense at 64k and 160k.
- 64k: -20 % with only GGML_CUDA_FA_SPARSE + MIN_HOST different from the dense arm, and no sparse op. So setting
  FA_SPARSE turns something on for every op before the threshold check. P115 (open) isolates it (never64 arm:
  MIN_HOST=1e9).
- Margin cost: +250 MiB moves the line from 46,592 to 34,560 cells. The sparse tables are sized for the host tail of
  the whole window, so the launcher must reserve them for every session.
- Today's trade on 8 GB with sparse on (notebook / #21): 64k 34.5 -> 23.0, 160k 9.7 -> 19.6, 245k 5.7 -> 11.6+ (with
  timing). Sessions below ~100k lose; deep sessions gain 2x or more.

## What it changed

- Posted on #21 (comment 6153630668) with options to shrink the margin: page 128 (0.5 KiB per cell), bounds in pinned
  host memory (read once per op), or tables that grow with depth plus a launcher that reserves only up to a set depth.
- Queued P115 (queue 69g5): dense64 vs never64 (FA_SPARSE + MIN_HOST=1e9) for the 64k overhead, and sparse245
  (MIN_HOST=32768) vs dense245 without OP_TIMING for the clean 245k speed.

## Toolbox (for the next model)

- Method: to test a depth threshold, run one depth below it and one above it on one server, and check the engage line
  in the log at each step (here the first ggml_cuda_fa_sparse_mask line at 160k).
- Method: when a switch-on arm loses at a depth where the feature never runs, the cost is in the switch, not in the
  feature. Add a "switch on, feature never" arm (P115 never64).
- Transfers: a sparse read path that reserves tables for the whole window costs shallow speed on a small card (here
  line -12,032 cells). Size the tables by depth, or put them in host memory.
