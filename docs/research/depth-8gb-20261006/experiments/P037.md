## Question

How many milliseconds per decode token does each op class cost? Which classes are worth fusing?

## Why

P36b estimated ~6 ms/token of small ops beside ~16.8 ms of mat-vecs; the op timer inflates small ops, so it cannot
give milliseconds.

## Plan and gate (as frozen before the result)

"Plain model, 8k window all in VRAM, CUDA graphs on, 256 tokens ignore_eos x3 per arm; one arm per op class skipped in
one-token graphs (outputs garbage by design: time only). Cost(op) = t(skip) - t(none) per token. Decode graph (sched
dump): 2,633 nodes/token: MUL_MAT 819 (incl. f32 Hadamard 1024 and bf16 alpha/beta), MUL 483, RMS_NORM 209, GET_ROWS
194, CPY 192, ADD 128, SWIGLU 112, SCALE 96, CONT 64. Reading: classes summing to >= 2 ms/token are fusion targets,
ranked by ms; < 0.3 ms ignored."

## Method

Per arm: start the raw server with `GGML_CUDA_SKIP_OPS`, three `/completion` requests ("Write a long story about a
lighthouse keeper.", n_predict 256, temperature 0, ignore_eos, no prompt cache), record `predicted_per_second`.
Arms bracketed by "none" at start and end.

Notebook reading: "decode = 15.8 ms ternary mat-vec + 2.8 ms small ops + ~3.5 ms rest, per token ... llama-bench tg256

~2.8 ms (-13%). Merging same-input mat-vecs (GDN qkv 10240 + gate 6144; attn q+k+v) moves 280 -> ~350 GB/s on ~3 ms
of them."

## Deviations, incidents, void runs

- P37: "the skip filter (ne[1]==1) never matched GDN / FA / ADD outputs - those rows are void." The ADD row has no
  number in the receipt.
- P37b: the MUL_MAT_Q arm (45.3-45.5) and the all-small-ops arm (45.3) did not move from "none": the filter still did
  not match. The notebook marks "first two passes void: filter missed".
- P37c is the valid pass.

## Verdict

No single small-op class is near 2 ms/token; all small-op classes together are 2.8 ms (+14.6 %: 51.7 vs 45.1 tok/s).
The ternary mat-vecs take 15.8 ms at 80 % of peak. The gate's fusion-target list is empty per class; the combined
small-op budget is ~2.8 ms.

## Corrections later

- 2026-10-09 decision (Cary agreed): "Measured ceilings (P37 skip tests): removing a whole small-kernel class gains
  0.5-1.7 %; all small kernels together +14 %, spread over ~1,200 kernels of ~2.3 us." The per-class figures come from
  the P37 first pass rows for classes the filter did match (e.g. RMS_NORM 46.25-46.47 vs none 45.29-45.64).
- P76: gate+up fusion in all 64 FFNs gave +0.2 %. Micro-fusions stopped; a megakernel stays a last resort.

## What it changed

The fusion target list (P41b census, P48 ADD+RMS_NORM+MUL fusion, later P76). No shipped change from P37 itself.

## Toolbox (for the next model)

- Method: a diagnostic build that skips op classes inside the CUDA graph (garbage output by design) gives the real
  per-class cost in milliseconds with graphs on. Bracket the arms with "none" runs. Verify that the skip filter
  matches (a skip arm that does not move is void, not "free").
- Model-specific: 2,633 graph nodes per token; 48 GDN + 16 attention layers; GDN and FA cost ~0.
- Transfers: before a fusion project, measure the ceiling (skip all small ops). Here the whole small-op budget was
  13 %, and each class alone was under 2 %.
