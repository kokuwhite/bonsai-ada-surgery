## Question

Can all 64 FFN layers use the fused gate+up+SwiGLU mat-vec (only 40 of 64 did), with identical output, and how much
decode does it give?

## Why

P55b census (corrected): "gate+up fused in only 40 of 64 FFN layers (24 run as two kernels) - small fusion target
(~1 %)". Agent read: "24 of 64 FFNs miss the gate/up/SwiGLU fusion because the allocator puts the GLU output on the
Hadamard activation block; the memory guard refuses (correctly: the q8 rows live there)."

## Plan and gate

Notebook: "Fix (prism-fuse c87233fc1 on 5251968b0): try_fwht_q8 moves the q8 rows to a held pool block when a GLU output
within 6 nodes overlaps; the GLU fusion check ignores the shared-activation overlap on the quantized mat-vec path only.
Switch GGML_CUDA_GLU_ALIAS_FUSE=0. Test build adds the census diagnostic (42ee8889f). Checks: test-backend-ops MUL_MAT,
GLU, MUL_MAT_VEC_FUSION (if present) on CUDA0; census: 64 gate-fused mat-vecs (was 40), SwiGLU kernels 48 (was 72);
plain raw server, -c 8192, quick_tps 4k x3 alternated switch 1/0; greedy texts (3 prompts, 300 tokens) identical
between 1 and 0. Gates: tests pass; census as expected; texts identical; decode not slower (expected +0.5-1 %)."

## Method

Wait for the build ("fuse exit 0"), copy to bin-fuse. test-backend-ops on CUDA0. Per switch value (1 then 0): one raw
server, 3 greedy /completion texts (300 tokens, cache_prompt false; prompts: ISO 8601 parser, heat pump, bash log
rotation), census of graph #2. Then quick_tps 4k x3 rounds alternated (f1, f0).

## Results

- Tests: MUL_MAT 1516/1516, MUL_MAT_VEC_FUSION 506/506, GLU "0/0 tests passed" (no GLU cases in this build).
- Census graph #2: switch 1: 1478 kernels, gate-fused mat-vec (mul_mat_vec_ptq1_0_pt<1,4,true,true>) x64, SwiGLU
  (unary_gated_op silu) x48; switch 0: 1526 kernels, gate-fused x40.
- Texts: identical (742ae8b25bc9, 35cd26a0accc, ee1bf6644910 in both).
- Decode 4k mean (tok/s): switch 1: 44.0 / 44.0 / 43.9; switch 0: 43.9 / 43.8 / 43.9.
Notebook: "tests MUL_MAT 1516/1516, MUL_MAT_VEC_FUSION 506/506; census 1478 vs 1526 kernels (64 vs 40 gate-fused);
greedy texts identical; plain decode 4k 44.0/44.0/43.9 vs 43.9/43.8/43.9. Held to ship with the next fusion (norm into
fwht quantize)."

## Deviations, incidents, void runs

- The GLU test op had no cases (0/0); not a failure, not a check either.
- The census_0/census_1 receipts show graph #2 of the plain server at -c 8192 (P55b had 1574 kernels on 008ac1112;
  this engine has 1526 with the switch off).

## Verdict

All gates pass (tests, census, texts, not slower). Gain +0.2 %, below the expected +0.5-1 %.

## Corrections later

Same day, the decision "stop micro-fusions; megakernel only as a last resort": "P76 gate+up fusion (64/64 FFNs,
identical text): +0.2 %. ... Neither ships (engine complexity, held pool blocks, for < 1 %). Gate+up fix kept on fork
branch fuse-gateup (c87233fc1) for a future megakernel effort."

Not shipped. Ended the micro-fusion line of work.
