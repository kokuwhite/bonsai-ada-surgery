## Question

With the desktop at 1280x1024 (~250-280 MiB returned), how many q4_0 positions can sit in VRAM without WDDM demotion or
a slide in decode?

## Why

The 21:41 baseline change (events file) showed clean idle VRAM of 323 MiB at 1280x1024 vs 561-608 MiB at 4K: ~15-17k
more q4_0 positions.

## Plan and gate

P11 sizing (measured): "q4_0 fixed 5,962 MiB (B: 6,743 server at N=38656 minus 680 head minus 101 staging); card usable
8,007 MiB (used+free); idle 323 MiB at 1280x1024. N for free F: (8007 - 323 - F - 5962 - 144) MiB / 17,280 B."
Arms (bin-turing, q4_0, CTX 131072, stock clocks + fan 100%): N=65280 (~500 MiB free) then N=77568 (~300 MiB free).
"Load per arm: 10 min alternating 4k / 16k / 48k greedy requests (p9_soak pattern + a 48k depth, inside the VRAM line for
both arms), nvidia-smi free and the server's shared GPU memory sampled every 5 s." Gates written before the run (quoted):
- "decode of the last 2 minutes within 3% of the first 2 minutes at every depth (WDDM demotion shows as a slide/cliff);"
- "shared GPU memory of llama-server does not grow beyond the pinned host tail ((131072-N) x 18,432 B + host buffers);"
- "min free VRAM never under 150 MiB;"
- "pass at 77568 twice -> that N is the default; else the largest passing N; the launcher constant/margin for a
  display-on-the-card 8 GB rig is derived from the passing arm."

P11b plan: "After P12. bin-turing, q4_0, N=77568, stock + fan 100%. Four 4-minute single-depth blocks: 4k, 64k, 4k, 64k
(each block warms its prefix once, then every request is a cache hit; 64k sits inside the 77,568 VRAM line). Server
shared GPU memory and card free sampled every 5 s. Gates: block-3 vs block-1 (4k) and block-4 vs block-2 (64k) mean
decode within 3%; shared memory flat; min free > 150 MiB. Pass -> 77,568 is the 8 GB default at 1280x1024 (two passes);
fail -> step down to 65,280 and repeat."

## Method

P11: p9_soak.py with depths 4000,16000,48000, 600 s per arm, 300-token greedy requests alternating code/prose prompts.
sample_mem.ps1 every 5 s: llama-server shared and dedicated GPU memory (performance counters) and card free.
P11b: one server, four 240 s blocks of p9_soak.py with one depth each.

## Corrections later

- P012 found a prefill anomaly at N=77,568 (237 tok/s at 4k vs 405 for C2). P014/P014b: a prefill cliff at ~269 MiB
  free (memory pressure), not seen in decode soaks. P014c: the cliff is not deterministic (load-time state).
- P020 used N=67,840 for the long mode; P027 moved it to N=53,248 with ub 1024 + f16 prefill. 77,568 never shipped.
- The decode-only soak gates of P11/P11b could not see the prefill cliff: the soak warms each prefix once and then
  measures cache hits.

## What it changed

The 8 GB long-context mode was set to 77,568 positions for the night (P012, P013 used it). The free-margin target of
~257 MiB used to size drafting arms (P012 step 2, P015, P022) comes from this pass.

## Toolbox

- Method: size N from a measured fixed cost and a free-VRAM target; soak in blocks (one depth per block, cache warm) so
  drift numbers compare like with like; sample the process's shared GPU memory to see WDDM demotion.
- Lesson: decode soaks do not test prefill. A margin that passes decode can still hit a prefill memory cliff (P014).
- Transfers: any WDDM (Windows) card with the desktop on it. Linux/TCC cards have no demotion but the same prefill
  scratch issue.
