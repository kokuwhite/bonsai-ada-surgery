## Question

P115 showed never64 (FA_SPARSE set, 0 sparse ops) -20.6 % below dense64. Which op takes the extra time?

## Why

The 2060 offered this op-timing diff on #21 with the P115 result, to point the engine fix.

## Plan and gate

Notebook (P115 entry): "P118 (queue 69g7, after P116b): OP_TIMING diff dense64 vs never64 (P115 env) -> which op
carries the always-on -20.6 %."

Script header: "Reading (declared before the run, no pass/fail): the op(s) whose ms/graph differ by more than 1 ms
between the arms."

## Method

Two servers (dense64 18:33, never64 18:38), quick_tps 64000 each (code, prose, bash); the last "op timing over 100
graphs" block from each server log.

## Verdict

DONE. Notebook: "Reading: with FA_SPARSE set, attention takes a slower path for every op even when no sparse mask is
built (likely 85d949f5e routing keyed on the config). Suggested on #21: route to the sparse path only when the op's
mask was built (same condition as min_host)."

## Corrections later

The "likely 85d949f5e routing" guess was wrong. The 4070 found the cause (#21, 00:53Z 2026-10-14): "It is not in the
kernel. Graph setup (ggml-cuda.cu, tier prefetch) leaves out every attention op that ggml_cuda_fa_sparse_eligible()
accepts. That function does not check MIN_HOST." Below the threshold the op got no sparse mask and no prefetch, and
with STAGE_MIN_Q=9 the decode op read the whole host tail in place over PCIe: the 7.8 -> 22.8 ms here. Fix: one
eligibility check for both places (9d9a968d9, in product-sparse 3ab0af3c2). The suggested fix condition ("only when
the op's mask was built") points the same way. P123 confirms it on 8 GB: 0 sparse ops at 64k and no -20 % (events
E28).

## What it changed

Placed the cost for the 4070. With the root cause (E28) the routing fix went into product-sparse 3ab0af3c2 (E29).

## Toolbox (for the next model)

- Method: an op-timing diff of "feature on, never fires" vs "feature off" places an always-on cost in one op.
- Pitfall: an op can be slow because of what the graph does around it (here: no prefetch), not because of its kernel.
  Read the op time as "where", not "why".
