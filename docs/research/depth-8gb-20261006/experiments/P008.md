## Question

Does extending the Ampere one-column PT override to Turing give the P007 gain without BATCH_INVARIANT, and does it change
nothing else?

## Why

P007: PT beats SOA_ISUM by 12.3% at one column on sm_75; Turing fell through to the Ada default.

## Plan and gate

P8 plan: "Change (fork bonsai-q8-product, ggml-cuda/common.cuh): the one-column override covers Turing as well as Ampere
(cc >= TURING && cc < ADA_LOVELACE). Build sm_75 with build\build_windows.ps1 into a separate bin (bin-turing\), bundle
untouched." Arms, q8_0 N=16384, stock verified: bundle BI unset (SOA, 36.7 reference) / new build BI unset (PT +
four-accumulator epilogue) / new build BI=1 (PT + warp reduce), alternating x2. Gates written before the run (quoted):
- "new build + BI=1 byte-identical to bundle + BI=1 (pt1 texts): proves the change touches nothing else;"
- "new build BI unset >= bundle BI=1 (41.2) by more than the run-to-run spread; report its gain over SOA;"
- "greedy texts of new build BI unset may differ from SOA (different summation order, as on Ampere); report KL of the
  new default vs the bundle default on the P6 recipe before it ships."

P8c plan (in "P8 (correction + plan)"): "llama-perplexity -b 1 -ub 1 (every token a one-column decode), -c 2048 --chunks
6, f16 K/V: base = bundle (SOA_ISUM), test = bin-turing (PT four-accumulator) and, as a scale, bundle with
BATCH_INVARIANT=1 (PT warp-reduce). Gate: new-vs-SOA mean KL below the q8_0-vs-f16 K/V KL on this card (0.000167) and
top-1 agreement above q8_0's 99.4% - i.e. the kernel change is smaller than the K/V precision this stack already accepts
as near-lossless."

P8b had no separate plan entry; the P8 incident entry names the test-backend-ops build.

## Method

P8: p8_build_ab.sh, same arm procedure as P007, memclock_probe 4k, 2 prompts x 400 x 2 reps. Arm order: s1 bundle SOA,
n1 new, b1 bundle + BI, n2 new, i1 new + BI. Text compare in the script.
P8 KL (first attempt at the KL gate): the P006 recipe on bin-turing, f16 and q4_0 K/V vs the f16 base.
P8b: p8b_then_p9.sh waits for the KL run and the tests build, then runs `test-backend-ops -o MUL_MAT -b CUDA0` on
build-turing, default and with GGML_CUDA_BATCH_INVARIANT=1.
P8c: p8c_kl_onecol.ps1 writes the bundle SOA base logits, then scores bin-turing and bundle + BI against it.

## Deviations, incidents, void runs

1. P8 incident: mixed-source test build killed. "The test-backend-ops build compiled from vendor/prism-llama while the
   working tree was switched to the PR branch (PrismML prism 6bfcd79 + the fix): a mix of two source trees. Killed before
   any test ran; tree restored to turing-pt-onecol (bc3e5aa); the PR branch claude/turing-pt-onecol (34a932b on prism
   6bfcd79) now lives in a separate worktree vendor/prism-pr. bin-turing (P8's binaries) came from the clean first build
   and is unaffected." Rule: "never switch a checkout that a running build or server reads; one worktree per branch."
2. P8 build note: the build recipe's pip line lacks nvidia-cuda-cccl; it was added (13.3.4).
3. The P8 KL gate as planned did not exercise the change (see correction).
4. P8c ran `--chunks 4` (script and result), not the planned 6. The context is 2k, not the 8-16k of the q8_0 reference.
5. The P7 plan named "tg128 in llama-bench" for the third arm; no llama-bench number is recorded for P8.

## Verdict

P8: "Turing fix built and measured - +13.7% decode over today's Turing default." P8b: kernel tests pass. P8c: "Recorded
as a statistical tie, not a pass." Reading: "two valid summation orders disagree on near-ties at this rate; the PT path
Ampere and drafting already ship differs from SOA by the same amount." "Proceeding with the PR (Cary: "absolutely
contribute to prism"), the exact numbers in its body."

## Toolbox

- Method: an engine fix ships with (1) speed A/B alternated, (2) byte identity under a variable that pins both builds to
  the same arithmetic (BI=1 here), (3) test-backend-ops for the op, (4) a KL receipt that really runs the changed path.
- Lesson: llama-perplexity's default ubatch never runs one-column decode kernels; use `-b 1 -ub 1` for decode-kernel KL.
- Lesson: one worktree per branch; never switch a checkout a build or server reads.
- Transfers: any Turing card (RTX 20xx, T4) with a llama.cpp fork whose one-column dispatch was tuned for Ampere/Ada.
- Model-specific: PTQ1_0 ternary weights (PT layout, #218).
