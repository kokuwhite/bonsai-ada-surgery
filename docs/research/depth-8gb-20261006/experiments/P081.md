## Question

Can a staging buffer for only the first part of the host tail keep 131k-class prefill to a chosen depth while the
262k window stops eating VRAM cells? Does staging vs in-place read change decode at equal N on Turing?

## Why

P77: staging off makes the window free but prefill past the f16 limit 2-3x slower; the f16 KQ mask also grows with
the window and the launcher did not count it.

## Plan and gate

Notebook: "Engine (new worktree prism-pstage on 5251968b0 + 0046): GGML_CUDA_KV_TIER_STAGING_FRAC=f (0..1 of each K/V
part): only the first f x part bytes of each host tail get a VRAM staging buffer; the rest of the host tail is mapped
in the alias to its own host pages (read in place). Host allocations split at that boundary (cuMemMap takes no
offset). The staged runs alone are registered for copies, so copy and write-back code is unchanged. Unset = today
(whole tail). GGML_CUDA_KV_TIER_STAGE_MIN_Q=q: attention ops with fewer than q queries skip staging and read in place
(isolates staging vs direct for decode at equal N). Unset = 0 = today.
Launcher: FixedMiB += (ctx - 131072) x ubatch x 2 B when ctx > 131072 (mask growth); staging term uses the cap.
Arms after the build (drafting preset): A 131k preset again; D 262k, staging cap = A's staged positions (80,896),
N from the fixed launcher; E = D with MIN_Q=2 (decode direct); F 131k, N 50,176, staging on, MIN_Q=2 (pairs with A).
Gates for a 262k default: D (or E) decode within 3 % of A at 4k-96k; prose prefill at 64k/96k/128k within 10 % of A;
trace min free >= 60 MiB; 0 one-token; texts at 32k identical to A (same engine bits up to the cap).
P80 (tail 2 at 200k) waits for this engine."

## Method

Wait for the pstage build; test-backend-ops FLASH_ATTN_EXT; arms A, F, G, D in order, quick_tps 4k/32k/64k/96k/128k
(D also 160k), VRAM trace every 10 s.

## Verdict

Mechanism pass (no over-commit at 262k, prefill fast to N+S). 262k-default gate FAIL (D decode -12 % / -7 % at 64k /
96k vs A).

## Corrections later

- P82: the packed KQ mask saves 108 MiB at 131k (240 MiB at 262k) and is exact with drafting.
- P84: packed mask + pool + partial staging: 262k beats the 131k preset -> 262k default (patch 0047 = partial staging).

## What it changed

Engine switch GGML_CUDA_KV_TIER_STAGING_FRAC (patch 0047) and the mask-aware launcher term, both in PR #13.

## Toolbox

- Lever: partial staging = stage the first S host cells in VRAM (fast f16 prefill to N+S), read the rest in place.
  It turns the window size into a RAM-only cost and keeps prefill fast to a chosen depth.
- Finding: on Turing, decode reads of host rows cost the same staged or in place at equal N (on the 4070, staging
  gave +28 % at decode). Decode depth speed is set by N (cells in VRAM).
- Transfers: any tiered KV cache; choose S by the depth where agent turns usually live.
