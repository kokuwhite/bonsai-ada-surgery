## Question

With the sparse memory cut (8d5b862fc) and the VRAM margin raised to cover it, does the sparse arm stay inside VRAM
for the whole run, do the ternary mat-vecs return to dense times, and does the 160k follow-up prefill recover?

## Why

P107: sparse attention saved 30 ms per graph at 245k, but the mat-vecs ran 2.5-24x slower after the VRAM reading
wrapped at the first sparse decode step. The 4070 (#21, 16:02Z) found two sparse-only allocations at the first sparse
op: page-bound tables (2 KiB per host cell: 227 / 393 MiB at 160k / 245k) and a whole-tail first fill (219 / 385
MiB). Fix 8d5b862fc: bounds in f16 (1 KiB per host cell: 114 / 196 MiB) and the first fill in 16,384-cell chunks (32
MiB); sparse fixed cost at 245k ~230 MiB. The 4070 asked for this run as "P110"; here it is P111 (P110 = the
post-move smoke).

## Plan and gate

Script header: "Until the launcher counts it: BONSAI_VRAM_MARGIN=475 (225 + ~230 + slack) in BOTH arms (same VRAM
line). Arms (one server each, 160k cold then extend to 245k): dense, sparse; OP_TIMING; nvidia-smi trace every 10 s.
Gate (declared here, before the run; from the 4070's #21 request): sparse trace min free > 0 MiB for the whole arm,
AND the ternary mat-vec MUL_MAT 17408x5120 in the sparse arm <= 1.1x the dense arm's time, AND the 160k 512-token
follow-up prefill in the sparse arm >= 100 tok/s (P106: dense 107, sparse 85). Report 245k decode sparse vs dense.
FLASH_ATTN_EXT op tests must pass first (else stop)."

## Method

Wait for receipts/build-sparse7.txt ("build ok"), copy tooling/build-sparse/bin to bin-sparse7 (+ missing DLLs from
bin-0046). test-backend-ops -o FLASH_ATTN_EXT. Per arm: an nvidia-smi trace (used, free) every 10 s; run_arm.sh with
quick_tps 160000 then 245000 on one server (code, prose, bash per depth, 400-token greedy decodes); the last "op
timing over 100 graphs" block from the server log (first 30 lines); trace min free with the wrap correction.

## Deviations, incidents, void runs

- Build: the run used 3299a0b4b (the 4070 pushed it at 11:40, after the plan), not 8d5b862fc. MIN_HOST is unset, so
  the code path is the same as 8d5b862fc. The script header names both.
- Ran before the 4070's D18 quality gates (copies, needles, sparse_edit CHECK). Op tests and the trace do not depend
  on them; quality on this build stays with the 4070.
- OP_TIMING is on in both arms; it slows decode (P106: 18.5 without vs 14.6 with at 160k), so 14.8 / 11.6 are not
  clean speeds. P112 gives clean 160k numbers; P115 (open) the clean 245k number.
- The 245k step was a full prefill, not an extend: quick_tps evaluated 243,896 tokens (ttft 1,822 / 1,828 s). The
  notebook says "extend prefill 133.8" and the #21 post says "+85k to 245k"; the receipts show the whole prompt.
- The margin moves the line to 34,560 cells (P107 at margin 225: 46,592, server log), so the dense 245k graph here (166.1 ms) is
  not equal to P107's (155.5 ms). Both arms of this run share the line.

## Verdict

PASS. Notebook: "Reading: the P102-P107 245k loss and the follow-up drop were entirely the over-commit. OP_TIMING
depresses decode (P106), so clean speeds come from P112." With the memory cut and counted, the mat-vecs are at dense
times (0.89x), the follow-up prefill is equal to dense at both depths, and attention at 245k drops from 105.5 to 43.6
ms per graph. The 475 margin left 106 MiB at 245k, consistent with the 4070's launcher rule (host cells x 1 KiB x
(64 / page) + 36 MiB).

## Toolbox (for the next model)

- Method: when a feature allocates at its first use (here the first decode step), a load-time free-VRAM check misses
  it. Trace free VRAM every 10 s through each arm and look for steps at the first use of the feature.
- Method: give both arms of an A/B the same margin, so the VRAM line (and the host tail) is the same.
- Transfers: a sparse read path needs its tables in the launcher's VRAM budget. Here 1 KiB per host cell at page 64
  plus a fixed 32 MiB fill buffer.
