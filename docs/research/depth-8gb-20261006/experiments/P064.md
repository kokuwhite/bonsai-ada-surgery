## Question

Which component makes fresh 60k prompts answer with 1 token: the f16 prefill path (patch 0038), lookup drafting, or
the shared CUDA pool?

## Why

P61: every fresh 60k request answered 1 token in both engines; P50 had one 1-token answer at 120k. Lead from P61:
the f16 prefill cap (32768) is crossed inside one fresh prefill.

## Plan and gate

Notebook (plan): "bin-tier, drafting preset, quick_tps --depth 60000 (fresh) x4 arms: F16=32768 + lookup (repro),
F16=0 + lookup, F16=32768 + BONSAI_LOOKUP=0, F16=0 + BONSAI_LOOKUP=0. Count 1-token answers.
Reading: only F16 arms fail -> patch 0038 bug (fix before anything ships; 8 GB preset sets it); all fail -> look at
0041 / long fresh prefill / checkpoints; none fail -> flaky, repeat x3."
Amendment before the run: "5th arm f16 + lookup with the shared CUDA pool off (launcher copy
start-server-maintest-nopool.ps1; 4070 session suspect 2)."

## Method

5 arms in order, one server each: f16_look, nof16_look, f16_nolook, nof16_nolook, f16_look_nopool. Each: quick_tps
--depth 60000 (fresh 59,953-token code prompt, then prose and bash 512-token prompts at that depth, 400-token
decodes). Count "(1 tok)" lines. Server stderr copied per arm.

## Deviations, incidents, void runs

- The server logs hold no GGML_CUDA_SHARED_POOL line (the env value is not logged); the pool state is known from the
  launcher copy used per arm.
- The engine bug itself was not found here. Notebook suspect: "pool blocks held across graphs, e.g. the FWHT/Q8
  context, in a LIFO pool shared with the draft context."

## Verdict

Notebook: "Patch 0037's GGML_CUDA_SHARED_POOL, set by the 8 GB preset (shipped in PR #6 / bundle-20261007-8gb),
breaks fresh long prompts with MTP drafting on this card."

## Corrections later

- P65 tried to isolate other components but was confounded (the launcher copy lost the pool mid-run).
- P67: the failure is intermittent (pool-on control passed 0/3 once; 7 of 10 pool-on runs failed).
- P68 / P69: candidate fix 142d5105d (poolsync, later patch 0045): 0/18 vs 18/18.
- P71: the P59 "wrong output" with --checkpoint-every-nt also came from the pool (P59 ran with the pool on).
- P54 (2026-10-09): the old tail-2 1-token reports (P18) also ran with the pool on; most likely the same race.

## What it changed

- Hotfix PR #10: the 8 GB preset no longer sets the shared pool; drafting fixed cost 6469 -> 6531 MiB (VRAM line
  down accordingly).
- The maintest launcher copy (used by queued jobs and fillers) got the hotfix (pool off) at 16:50:22.
- Later (P83, P84, P85, PR #13) the pool returned on 8 GB with engines that have patch 0045.

## Toolbox

- Method: a factorial bisect on the cheapest reliable repro (one fresh 60k prompt, 3 requests per arm), with one arm
  per suspect, and an amendment slot for a late suspect. Count failures, not speed.
- Lesson: an env-var feature that shares memory between two contexts on different streams (target + draft) needs a
  stream-order guarantee. Ada (4070) did not show the race (20/20), Turing showed it 3/3: test races on the slow card.
- Transfers: any model with a draft context (MTP, EAGLE, small draft model) that shares a memory pool.
