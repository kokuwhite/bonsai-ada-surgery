## Question

(1) Is the -20 % that P112 found at 64k (FA_SPARSE set, no sparse op run) a cost of sparse selection, or an always-on
cost of the env? (2) What is the sparse speed at 245k without op timing (P111 had it on)?

## Why

P112: with MIN_HOST=32768 no sparse op ran at 64k (host tail ~29.5k cells), but decode was 23.0 vs dense 28.8. P111
measured 245k with OP_TIMING on (11.6 vs 5.2), which slows decode (P106).

## Plan and gate

Notebook (P112 entry): "P115 (queue 69g5, gate in its header): dense64 vs never64 (FA_SPARSE + MIN_HOST=1e9: sparse
never runs) isolates the 64k overhead; sparse245 (MIN_HOST=32768) vs dense245, no OP_TIMING, for the clean 245k
speed."

Script header: "Gate / reading (declared here, before the run): if never64 is >= 5 % below dense64, the 64k cost is an
always-on overhead of FA_SPARSE (engine fix on the 4070), not sparse selection. sparse245 vs dense245: report (expect
>= 2x)."

## Method

Four arms, one server each, in this order: dense64 (17:08), never64 (17:13), sparse245 (17:19), dense245 (17:51).
quick_tps at one depth per arm (64000 or 245000; code, prose, bash, 400-token greedy decodes). Per arm: an nvidia-smi
trace (used, free) every 10 s and a count of `ggml_cuda_fa_sparse_mask` lines in the server log.

## Deviations, incidents, void runs

- None in the run. Both 245k arms were full cold prefills (243,896 tokens), as planned.
- The plan said "245k cold"; both 64k arms were cold too (64,009 tokens), so the 64k pair compares like with like.

## Verdict

PASS (reading as planned). Notebook: "Gate: never64 >= 5 % below dense64 -> YES: always-on overhead of FA_SPARSE
(engine, 4070). 245k: 2.68x." Posted on #21 with candidates (85d949f5e MMA tile map, per-op entry work before the
min_host check, mask copy) and an offer to run an op-timing diff.

## Corrections later

P118 put the whole cost in FLASH_ATTN_EXT (7.8 -> 22.8 ms per graph). The 4070 then found the cause (#21, 00:53Z
2026-10-14): graph setup leaves every op that `ggml_cuda_fa_sparse_eligible()` accepts out of the tier prefetch, and
that check ignored MIN_HOST. Below the threshold an op got no sparse mask and no prefetch, so with STAGE_MIN_Q=9 the
decode op read the whole host tail in place over PCIe (4070: "It is not in the kernel."). The cause was not among
the candidates named in the P115 post.
Fixed in product-sparse 3ab0af3c2 (9d9a968d9); P123 shows 0 sparse ops at 64k on it (events E28, E29).

## What it changed

- 245k sparse 2.68x dense (clean) is the headline number for sparse on 8 GB.
- Queued P118 (op-timing diff dense64 vs never64).

## Toolbox (for the next model)

- Method: to tell a feature's fixed cost from its work, run an arm with the feature on and its trigger set so that it
  never fires (here MIN_HOST=1e9), and count the feature's log lines (0 here).
- Method: take headline speeds without op timing; use op timing only to place a cost.
