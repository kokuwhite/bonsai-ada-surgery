## Question

Does patch 0043 (f16 prefill path only for ops with >= 64 queries) keep the Turing prefill speed and raise
file-rewrite decode with lookup drafting, as it did on the 4070?

## Why

P58 (planned, superseded by this P60) asked the same question: patch 0038 converts the cache to f16 when Q->ne[1] > 8.
A lookup verify batch has 33 columns, so each verify step can take the f16 path. Main b8ba790 (Ada, #330 data) showed
lookup verify batches -9 to -10 % on file rewrites with GGML_CUDA_FA_PREFILL_F16. The 4070 measured 0043:
lookup file-rewrite decode 195.4 -> 212.4 tok/s, prefill same, 7/7 same text. The 12 GB session asked for the
Turing number on PR #9.

## Plan and gate

Notebook (plan): "A/B on the 2060: lookup on, GGML_CUDA_FA_PREFILL_F16=32768 (preset), bin-tier (8a6d2ea12, the
current bundle) vs bin-minq, 2 rounds alternated, lookup_ab.py at depth 0 and 16000, plus quick_tps --depth 30000
(one ~30k prefill) per binary."
Gate (the 12 GB session's): "minq keeps the Turing prefill (30k prefill within 2 %) and file-rewrite decode goes up;
same text hashes. Pass -> report on PR #9; he ships it as patch 0043. P58 superseded (same question)."

## Method

- Build both engines (tooling/build-tier, tooling/build-minq), copy missing DLLs from bin-lookup.
- Order: round 1 tier, round 1 minq, round 2 tier, round 2 minq. Per round and engine: one server start, lookup_ab.py
  at depth 0 then 16000 (11 items each: 4 quote, 3 plain, 4 edit; greedy, thinking off), then a new server start and
  quick_tps.py --depth 30000 (one fresh ~30k code prefill, then 512-token prose and bash prompts, 400-token decodes).
- Reading: decode tok/s per item, text sha per item, prefill tok/s of the 30k code prompt.

## Deviations, incidents, void runs

- The run used the launcher copy that still set GGML_CUDA_SHARED_POOL=1 (removed at 16:50:22 the same day, P64).
  The pool race (P64 to P69) was not known yet.
- Observation in this record (not in the notebook): sha bbf7b9093069 is the same 2048-token text that P59 got for all
  four edit items with the pool on, and that P61 got for the fnmatch.py edit at 30k. The round-2 shlex.py edit
  "difference between rounds" is most likely the same pool race, not min-Q.

## Verdict

Notebook: "Gate (decode up) FAIL on Turing, neutral -> no objection to 0043 for Ada. Posted on PR #9."
Prefill: within 0.2 % (gate part pass). Decode: no gain on Turing (gate part fail). Texts: same per round.

## Corrections later

- P61 and P70 repeated the comparison. P61 found 1-token answers in both engines (the pool race). P70 reran it with
  the pool off: min-Q neutral on Turing again (0/66 one-token, text identical).

## What it changed

Nothing on 8 GB. Data posted on PR #9; patch 0043 shipped by the 4070 session for Ada (in bundle-20261008-8gbfix,
see P72).

## Toolbox

- Lever: the query-count threshold for the f16-converted prefill path. On Turing the verify batches (33 columns)
  did not slow down with the f16 path, so the threshold change gives nothing here; on Ada it gave +8.7 %.
- Model-specific: the 33-column verify batch comes from lookup drafting (32 tokens + 1).
- Transfers: test any "batch-size threshold" kernel switch per GPU generation; the effect sign differs between
  Turing and Ada. Always check text shas per item and per round, and record the pool / launcher state.
