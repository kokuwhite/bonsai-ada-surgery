## Question

Does the real q3_0 KV type pass the backend op tests, and does it cost as little perplexity as the P100 fake 3-bit
bound predicted? Does 4k decode still work and at what speed?

## Why

P100: a fake 3-bit grid on q4_0 storage cost -0.02 % PPL at 64k (+0.60 % at 16k); a real 3-bit type (~3.5 bpw vs
4.5) would give ~22 % fewer bytes per cell: VRAM line ~+28 % (58k -> ~75k) and -22 % PCIe bytes, ~1.25-1.3x decode at
mid/deep depth. Cary approved the type (2026-10-10 evening: "go on all three depth levers (sync fix, verify-batch page
skip, 3-bit KV)"). The agent's work was stopped in the 2026-10-11 cleanup and saved as WIP 6a4851286; it was built in
the background during P104.

## Plan and gate

Notebook: "q3_0 build (kv-q3-0 6a4851286) OK during P104. P108 (queue 69f, after P107): q3_0 test-backend-ops; PPL
q3_0 vs q4_0 same bin at 16k / 64k; 4k decode raw server q3_0 vs q4_0. Launcher not used (its CellBytes does not
know q3_0 yet)." Script header: "1. test-backend-ops (q3_0 cases: SET_ROWS, GET_ROWS, CPY, FLASH_ATTN_EXT) vs CPU. 2.
perplexity q3_0 vs q4_0 on the same binary, wikitext-2: 16k (all chunks), 64k (2 chunks). 3. decode sanity: raw
llama-server -c 8192, quick_tps 4k, q3_0 vs q4_0." No numeric gate written; the P100 reading for scale: 3-bit < ~1 %
PPL at 64k.

## Method

1. Copy tooling/build-q3kv/bin to bin-q3kv (+ missing DLLs from bin-0046).
2. test-backend-ops -o SET_ROWS / GET_ROWS / CPY / FLASH_ATTN_EXT -b CUDA0 -p q3_0: "tests passed" line and FAIL
   count per op.
3. llama-perplexity at 16,384 (all chunks) and 65,536 (2 chunks) for q4_0 then q3_0, VRAM line pinned at 45,056
   (same settings as P100).
4. run_arm.sh with a raw llama-server (-c 8192, all in VRAM) for q4_0 and q3_0; quick_tps at 4000; mean decode and
   one-token count.
