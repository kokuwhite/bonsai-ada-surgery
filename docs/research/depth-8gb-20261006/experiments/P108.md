## Question

Does the real q3_0 KV type pass the backend op tests, and does it cost as little perplexity as the P100 fake 3-bit
bound predicted? Does 4k decode still work and at what speed?

## Why

P100: a fake 3-bit grid on q4_0 storage cost -0.02 % PPL at 64k (+0.60 % at 16k); a real 3-bit type (~3.5 bpw vs
4.5) would give ~22 % fewer bytes per cell: VRAM line ~+28 % (58k -> ~75k) and -22 % PCIe bytes, ~1.25-1.3x decode at
mid/deep depth. Cary approved the type (2026-10-10 evening: "go on all three depth levers (sync fix, verify-batch page
skip, 3-bit KV)"). The agent's work was stopped in the 2026-10-11 cleanup and saved as WIP 6a4851286; it was built in
the background during P104.

## Plan and gate

Notebook: "q3_0 build (kv-q3-0 6a4851286) OK during P104. P108 (queue 69f, after P107): q3_0 test-backend-ops; PPL
q3_0 vs q4_0 same bin at 16k / 64k; 4k decode raw server q3_0 vs q4_0. Launcher not used (its CellBytes does not
know q3_0 yet)." Script header: "1. test-backend-ops (q3_0 cases: SET_ROWS, GET_ROWS, CPY, FLASH_ATTN_EXT) vs CPU. 2.
perplexity q3_0 vs q4_0 on the same binary, wikitext-2: 16k (all chunks), 64k (2 chunks). 3. decode sanity: raw
llama-server -c 8192, quick_tps 4k, q3_0 vs q4_0." No numeric gate written; the P100 reading for scale: 3-bit < ~1 %
PPL at 64k.

## Method

1. Copy tooling/build-q3kv/bin to bin-q3kv (+ missing DLLs from bin-0046).
2. test-backend-ops -o SET_ROWS / GET_ROWS / CPY / FLASH_ATTN_EXT -b CUDA0 -p q3_0: "tests passed" line and FAIL
   count per op.
3. llama-perplexity at 16,384 (all 18 chunks) and 65,536 (2 chunks) for q4_0 then q3_0, VRAM line pinned at 45,056
   (same settings as P100).
4. run_arm.sh with a raw llama-server (-c 8192, all in VRAM) for q4_0 and q3_0; quick_tps at 4000; mean decode and
   one-token count.

The server is 32 MiB smaller with q3_0. That is 8,192 cells x (18,432 - 14,336) B = 32 MiB, so the cache size is as
designed: 14,336 B per position (16 layers x K,V x 4 heads x 8 blocks x 14 B) vs 18,432 for q4_0 (-22 %).

## Deviations, incidents, void runs

- Ran two days after the plan: the stop for the move (2026-10-11 11:50) came before P108 started, and P110 and the

- Builds beside the run: the 8d5b862fc build (tooling/build-sparse) ran from 11:08:50 to 11:10:40 (queue NOTE lines;
  receipts/build-sparse7-8d5b862fc.txt), during the op tests. The 3299a0b4b rebuild finished at 11:36:29
  (receipts/build-sparse7.txt), during the 16k q3_0 perplexity run (11:32-11:46). Op tests and perplexity values do
  not depend on CPU load. The decode arms (12:12-12:14) ran with no build. The notebook says "The 8d5b862fc build ran
  beside the PPL part only"; the queue log puts that build in the op-test part and the 3299a0b4b rebuild in the PPL
  part.
- Each perplexity log starts with "common_fit_params: failed to fit params to free device memory: n_gpu_layers
  already set by user to 99, abort". This is the parameter-fit step giving up because -ngl was set; the run then used
  -ngl 99 as given. The summary filters this line.
- The decode arms use a raw server with no drafting and an 8k window, so 43.9 tok/s is not comparable with the
  launcher numbers (51-54 tok/s at 4k with drafting).

## Verdict

PASS. Notebook: "Verdict: PASS (exact kernels; quality cost within the fake-bits bound). Bytes: 14,336 per position vs
18,432 (-22 %)." The real type matches the P100 bound at both lengths (16k +0.56 % vs +0.60 %; 64k +0.03 % vs
-0.02 %), well under the ~1 % scale at 64k. 4k decode is equal (43.8 vs 43.9). The depth gain (more cells in VRAM,
fewer PCIe bytes) is not measured here: P114.

## Toolbox (for the next model)

- Method: bound the quality of a new KV format with a fake-bits run on an existing format first (P100), then build
  the real type and check op tests, the same PPL protocol on the same binary, and a decode sanity run before any
  launcher work. Here the fake-bits bound predicted the real type to within 0.05 percentage points.
- Check: the server size difference between two KV types at a fixed window equals cells x (bytes per cell
  difference). Here 32 MiB at 8,192 cells.
- Model-specific: q3_0 targets this model's 16 attention layers (4 KV heads x 256); the gain on 8 GB is more cells in
  VRAM and fewer PCIe bytes per host cell.
