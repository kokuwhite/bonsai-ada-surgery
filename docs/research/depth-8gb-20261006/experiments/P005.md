## Question

At the same VRAM budget, which gives the best decode at depth: more q8_0 positions (A), twice as many q4_0 positions
(B), or q4_0 plus the MTP draft head (C)?

## Why

P001/P002: past the VRAM line decode falls 2.4x-11x. q4_0 cells are half the size of q8_0 cells. The MTP head speeds up
decode but costs VRAM. sudoingX's 3060 finding: draft 1.

## Plan and gate

Budget: the P001 serve's 6,656 MiB on the card (~500 MiB left free). CTX 131072 for all arms. Pinned N per arm:
- "A: q8_0, no head, N=16384 (P2 is its record; re-measured here in the same session for comparability)"
- "B: q4_0, no head, N=38656 predicted ((782 MiB - 131072 x 1152 B) / 17280 B per cell)"
- "C: q4_0, ProCreations head, draft 1 (sudoingX's 3060 finding), tail draft 2, draft window 16384, N sized at load to
  the same 6,656 MiB (head cost measured, not assumed)"
GGML_CUDA_BATCH_INVARIANT=1 in every arm. Measures: server VRAM at load and min free during the run; quick_tps decode
at 4k / 16k / 32k / 64k (3 prompts). Gates written before the run (quoted):
- "every arm within 6,656 MiB +/- 64 at load (else re-pin and re-run that arm);"
- "C's greedy texts byte-identical to B's at 4k (drafting must be lossless at the same KV type);"
- "decision: the default is the arm with the best decode at 32k (a long-chat depth past A's line) unless another arm
  beats it by >25% at 4k AND 16k; the losing arms stay documented modes. q4_0 as default additionally needs this card's
  KL receipt (P6) to repeat the 12 GB finding (~1 flipped top token in 48), stated in the README row."

### P5b plan (written after the C vs B difference, before arm D)

"C (mtp-procreations file, draft 1) differs from B (plain file, no draft) at greedy, both q4_0 + BATCH_INVARIANT: prose
splits at char 55 ("by moving heat" / "by continuously removing heat"), code at char 591. Arm D: the mtp file, SPEC=0,
GGML_CUDA_BATCH_INVARIANT=1 set by hand, q4_0, N=16384, probe only."
"Reading, decided before the run: D == B and D != C -> drafting is not lossless on this card (a correctness bug, blocks
the head on 8 GB until fixed); D == C and D != B -> drafting is lossless and the grafted file's graph shifts numerics
(file-level finding, not a draft bug); D equal to neither -> nondeterminism; re-run B and D once each before reading."

## Method

Each arm: stop any server, wait for idle VRAM, serve, record used/free after load, run memclock_probe.py once (4k
filler, code + prose, 400 tokens, 1 rep, texts saved), then quick_tps.py at 4k, 16k, 32k, 64k; card free VRAM sampled
every 5 s; draft acceptance read from the server log. Arm order as run: A (invalid), B, A-r2 (invalid), A-r3, C sizing
(N=8192, failed), C at N=16384, D.

## Verdict

P5: B is the 8 GB default candidate (best decode at 32k, 38,656 positions in VRAM), subject to P006. C is faster in VRAM
but costs ~600 MiB over budget and leaves 144 MiB free.
P5b at the time: "MTP drafting is not lossless on Turing; the head is blocked on this card."

## Corrections later

- P5b correction (same evening, after P8 result): "the C vs D difference is documented behaviour on every card, not a
  Turing bug." docs/Q8_FULL_CONTEXT.md:88 and PR #322's body: drafting is not bit-identical to not drafting, stock
  kernels included; attention's KV split follows the kernel instance (1-query decode vs multi-query verify) and the
  padded KV length; differences are rounding-level and every continuation is a valid greedy decode. BATCH_INVARIANT keeps
  only the PTQ1_0 weight path exact. P5b's gate ("C byte-identical to B") was written from the handoff's "greedy output
  identical to no draft", which overstates the docs; README line 74 ("lossless speculative decoding") does too (flagged
  to Cary, not edited). "Corrected reading: the head is not blocked by correctness. It stays out of the 8 GB default for
  the P5 reasons (decision rule picks B; 144 MiB free). The right gate for a drafting mode is task quality / KL, not byte
  identity."
- P006 met the q4_0 condition; B became the 8 GB default that evening.
- P012 (later that night) made the head cheap (q4 head, pool) and moved the default to drafting (C2), then P015 to
  tail 1 at N=47,360. B became the long-context mode (P011: N=77,568; later N=67,840 in P020 and N=53,248 in P027).
- P007 found that GGML_CUDA_BATCH_INVARIANT=1 alone selects a faster one-column kernel on Turing, so A here is not
  comparable with P002 (which ran without it); the notebook says so in the P5 result.

## What it changed

- Default candidate for 8 GB: q4_0 K/V, no head, ~38.6k positions in VRAM (confirmed by P006).
- Rig scripts: stop.ps1 / serve.ps1 / arm-script guards (incident 1). Every later arm script waits for idle VRAM.
- The decision rule ("best at 32k unless > 25% at both 4k and 16k") is reused in P012.

## Toolbox

- Method: compare KV precision against positions at equal VRAM, not at equal N. On a small card the depth where the
  VRAM line falls decides the winner.
- Method: a four-arm text test (B plain, C drafted, D grafted-file-undrafted) separates "file changes numerics" from
  "drafting changes numerics".
- Lesson: drafting with an attention verify batch is not bit-identical to plain decode on any card; use quality or KL
  as the gate for drafting modes, not byte identity.
- Lesson (rig): a stop script that silently fails stacks servers on the card; always verify idle VRAM before a load.
- Model-specific: the MTP head on Bonsai 27B costs ~95 MiB of weights resident plus ~870 MiB for drafting (draft
  context, GDN snapshots, compute) at tail 2 on this engine.
