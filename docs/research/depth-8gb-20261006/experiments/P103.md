## Question

Does turning CUDA graphs off only for graphs whose attention reads the host tail (so the tier prefetch pipeline runs)
speed up decode past the VRAM line on 8 GB, without a loss at shallow depth?

## Why

4070 (issue #22): "CUDA graphs on (shipped) keep the tier prefetch pipeline off; graphs off at 192k on 12 GB: 19.8 ->
25.0 tok/s." Fork tier-graphs 4715804d6 does it per graph. Notebook note before the run: "P102 dense ran graphs off
and got 5.7 tok/s at 245k = P86b with graphs on, so on PCIe 3.0 the overlap may give little."

## Plan and gate

Notebook: "Arms (main 262k launcher, defaults): new vs old, 4k/32k/128k/192k/245k; 192k lookup off for both. Gate
(4070's): no loss at 4k/32k, gain or no loss past the line, same text; else the 8 GB recipe sets
GGML_CUDA_KV_TIER_GRAPHS=1. Built during P102d (CPU -j 4; P102d decode figures may carry a little noise)."
P103b (notebook): "P103b (queue 69b): alternated new/old x2 at 4k/32k." Script: "is the -3 % / -5 % at 4k / 32k in
P103 (new vs old, one run each, an hour apart) real? Alternated runs."

## Method

- P103: run_arm.sh per arm with quick_tps.py at 4000 -> 32000 -> 128000 -> 192000 -> 245000 (new, then old), then
  192000 only with lookup off (new_lkoff, old_lkoff). Per arm: free VRAM and server private MiB every 10 s; count of
  the switch log line ("attention reads the host tail").
- P103b: new_r1, old_r1, new_r2, old_r2 at 4000 -> 32000.

## Deviations, incidents, void runs

- The switch line is GGML_LOG_INFO and does not reach the server log (same as the sparse INFO line), so engagement was
  read from the speed only. "use WARN". The 4070 then made it WARN in release candidate 90ca41e40 (patch 0053).
- P103 4k/32k: one run each, an hour apart; "new is in our usual range (P85 50.8/45.8, P96 51.5/51.3); old ran high".
  P103b re-tested it.
- The q3_0 agent's -j 4 compile ran during P103's speed run; the 2026-10-11 cleanup stopped it.
- The plan's gate includes "same text"; the scripts do not compare texts (quick_tps records speed only), and the
  notebook result does not report a text check.

## Verdict

P103 (notebook): "tier-graphs on 8 GB: +8 to +16 % past the line; shallow -3/-5 % to re-check ... 512-token prefill
equal. 0 one-token; VRAM min 62-72 MiB; private peak 14.85 GB."
P103b (notebook): "4k / 32k new vs old alternated x2: 53.9/54.0/53.8/53.7 and 48.2/48.3/48.2/48.3 -> identical; P103
shallow gap was noise. Tier-graphs gate PASS on 8 GB; posted on #22 (bundle can ship)."

## Corrections later

None. The P102 note ("on PCIe 3.0 the overlap may give little") was too pessimistic: +8 to +16 % past the line.

## What it changed

Patch 0053 (graphs off only for host-tail graphs) for both recipes; 4070 numbers on #22: 192k 23.6 -> 29.4, 250k 12.7
-> 14.6, 4k/32k unchanged. docs/DEPTH.md: "RTX 2060 SUPER, 8 GB recipe: 128k +16 %, 192k +9 %, 245k +8 %; 4k / 32k
unchanged."

## Toolbox (for the next model)

- Lever: CUDA graphs capture a fixed op sequence, which blocks the runtime's async prefetch of the offloaded KV tail.
  Turn graphs off only for graphs that read offloaded rows; keep them for the rest.
- Method: a shallow-depth difference from one run per arm an hour apart is not evidence; alternate arms (ABAB).
- Model-specific: the gain is set by the PCIe share of a decode step (4070, PCIe 4.0: 23.6 -> 29.4 tok/s at 192k;
  here, PCIe 3.0: +8 to +16 % past the line).
- Transfers to any tiered/offloaded KV design with CUDA graphs.
