## Question

With every decode op on the fast sparse path (lookup off: MTP verify = 2 queries), how fast is decode at 245k with
B = 8192 against dense? Then, for each new prototype build: is the per-op host sync gone, and does decode beat dense?

## Why

P101: quality equal at 245k, but code items ran lookup verifies outside the FAST path, so no speed gain. P102 removes
lookup to put every decode op on the fast path. Each later letter run tests a 4070 build that fixes the overhead the
previous run found.

## Plan and gate

- P102 (notebook, in the P101 partial): "P102 (queue 66): decode speed at 245k with lookup off (MTP verify = 2
  queries): dense / s8192 in place / s8192 staged." No numeric gate; speed-up reported.
- P102b (notebook): "sparse arm on fa-sparse-proto c084831aa (device selection, no per-op sync, write tracking),
  lookup off, 245k; dense baseline = P102 dense. 4070 dense as shipped with lookup on: 19.7 tok/s at 192k, 12.7 at
  250k (PCIe 4.0)."
- P102c (notebook): "ae61c4cf3 (no syncs; verify <= 64 stages kept pages), 245k: s8192 lookup off / dense lookup on /
  s8192 lookup on; checks: no sync-per-write warning, fast: WARN line." 4070 on 71371d4cb for scale: lookup off 192k
  dense 22.8 vs sparse 21.5; lookup on sparse 14.4 vs dense 19.7.
- P102d (notebook): after the P102c sync warning, "offered BONSAI_SPEC=0 and KV_TIER_REDIRECT=0 isolation arms";
  "P102d running (dense no-MTP, s8192 no-MTP, s8192 redirect off)". Script: which path makes "set_rows indices are
  not a host-set input: one sync per K write"?
- P102e (notebook): "fa-sparse-proto c803e03ea (sync-free index copies, MMA tile skip, SINKS): s8192 lookup off / on
  (TILE_SKIP=1) / + SINKS=4096; sync warning count and fast: line." Later: "Build for P102e: d6c6e9f01 (64-cell
  tile-map entries, sparse ops always use the MMA tile map, includes 2f47c38b7)."

## Method

run_arm.sh per arm: one server, quick_tps.py at depth 245000 (one cold ~243,896-token code prompt, then 512-token
prose and bash follow-ups; 400-token greedy decodes; mean decode = code / prose / bash). From P102c on: count of
"one sync per K write" warnings in the server log and the last "GGML_CUDA_FA_SPARSE ... fast:" WARN line.

## Verdict

- P102 (notebook): "the 87e2ac160 prototype halves decode at 245k (per-op host sync overhead) ... decode dense 5.7 /
  s8192 in place 2.9 / s8192 staged 2.9 tok/s; 512-token prefill 79 / 39 / 39 tok/s; acceptance 0.77 / 0.76. 0
  one-token. The two sparse arms are identical to 0.1 tok/s -> the per-op page-bound host copy + stream sync sets the
  speed, not the read path."
- P102c: "ae61c4cf3 sparse B=8192 lookup off 2.6 tok/s vs dense 5.7; the "set_rows indices are not a host-set input:
  one sync per K write" warning appears in both sparse servers after the first 4-query op (draft/verify path?)."
  "s8192 lookup on 2.6 tok/s (= lookup off; quick_tps plain prompts rarely draft by lookup); sync warning 1 in each
  sparse server."
- P102d: "s8192 with GGML_CUDA_KV_TIER_REDIRECT=0: 2.5 tok/s, sync warning still 1 -> the tier redirect is not the
  source. ... Remaining suspect: the MTP draft/verify path; 4070's 2f47c38b7 (index copies from set_tensor_async /
  scheduler input copies) targets it -> P102e."
- P102e: "d6c6e9f01 removes the sync; sparse decode still slower than dense on 8 GB. 245k, line 43,520, host tail
  ~197k: dense 5.7 tok/s (512 prefill 79); s8192 P64 lookup off 4.3 (39); lookup on 4.3 (39); + SINKS=4096 5.2
  (6.2!). Sync warnings 0; fast path engages (128 of 3077 pages kept). Reading: our decode ops have 2 queries (MTP
  tail 1) -> vec kernel, whose tile skip is 128 cells: with P=64 a tile is skipped only if both pages are dropped; 4070
  tail 4 -> 5-query MMA ops with the 64-cell map. Also the 512-token prefill halves with sparse on (MAXQ default:
  attention dense) -> a write/bound-refresh cost. Posted on #21 with options (64-cell vec skip, or MMA for >= 2q)."

## Corrections later

- P105 / P106: at 160k sparse is 1.9x dense (18.3 / 18.5 vs 9.7) with d6c6e9f01 and 028f606fc; at 245k 028f606fc gives
  4.9 (dense 5.7). The follow-up prefill drop is not write tracking (P106 NOTRACK arm). P107 times the ops at 245k.
- The "prefill halves" reading: P106 found it comes with FA_SPARSE set (85 vs 107 at 160k), not from tracking.

## What it changed

Each run sent its finding to #21 and the 4070 fixed the next item: per-op sync (87e2ac160) -> device selection
(c084831aa, 9f2df0a8f) -> no per-write sync (2f47c38b7, in d6c6e9f01) -> 64-cell tile map (d6c6e9f01) -> vec warp
skip (028f606fc, P106). P105 amended with tail-4 arms to test the vec-vs-MMA reading.

## Toolbox (for the next model)

- Method: an A/B where two arms with different read paths give the same speed to 0.1 tok/s means a fixed overhead
  (sync, copy) sets the speed, not the path under test.
- Method: count a specific warning line per server to localise a sync source; isolate with switches (no MTP, no
  redirect).
- Model-specific: MTP tail 1 gives 2-query decode ops, which run on the vec kernel (128-cell tiles); on the 4070 the
  12 GB recipe's tail 4 gives 5-query ops on the MMA kernel. A sparse kernel must skip at the page size in the kernel
  that the decode ops actually use.
- Transfers: on 8 GB the launcher needs drafting for the 262k window, so no-draft arms must also set a window that
  fits the test depth.
