## Question

Does bin-chunk with the chunk path off give the same depth-0 texts as the engine without the chunk patch?

## Why

P91 found depth-0 plain texts different from P85 (8/11) with the PR #19 launcher, although at depth 0 no op has more
than 32,768 KV cells, so no op should take the chunk path.

## Plan and gate

No plan entry in the notebook. The script header is the frozen plan: "P92: does bin-chunk with the chunk path OFF
give the release text? bin-pmask (d90e35528) vs bin-chunk (+0051/0052), same launcher (262k test launcher, does not
set GGML_CUDA_FA_CHUNK), lookup_ab at depth 0 (all in VRAM, < 32k)." Implied gate: 11/11 same text.

## Method

Three servers in order pmask, chunkoff, pmask2 (one server each, same launcher). lookup_ab.py at depth 0 (11 items:
4 quote, 3 plain, 4 edit; greedy, thinking off). Compare text shas per item with the first pmask arm.

## Deviations, incidents, void runs

None in the run. The notebook has no plan entry for P92 (only the script).

## Verdict

Notebook: "P92: bin-chunk with GGML_CUDA_FA_CHUNK=0 = bin-pmask = bin-pmask rerun (11/11 each, depth 0)." The chunk
binary with the switch off gives the same texts as the engine without it. But bin-pmask itself gave the Oct 10
texts, not the Oct 9 (P85) texts: "bin-pmask with the same launcher gave the Oct 9 texts on Oct 9 and the Oct 10
texts on Oct 10. Not the engine, not the switch."

## Corrections later

P94 found the cause class: state carried across requests in one server (request history), not the engine.

## What it changed

Cleared the chunk binary for the bundle (with P93). "Lesson: compare texts only within one session window (same
day, alternated arms), as P82/P89/P92/P93 did."

## Toolbox (for the next model)

- Method: to blame a patch for a text change, run old binary / new binary with the switch off / old binary again in
  one session. If the two old-binary runs agree with the new one, the patch is clean and the reference is stale.
- Transfers to any model and card.
