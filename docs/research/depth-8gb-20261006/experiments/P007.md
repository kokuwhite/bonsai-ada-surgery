## Question

Is the planar PT one-column kernel faster than the Ada-tuned SOA_ISUM kernel on sm_75?

## Why

Observation: clean arm A-r3 of P005 (q8_0, N=16384, GGML_CUDA_BATCH_INVARIANT=1) probed 42.80 tok/s at 4k vs 36.7-37.5
for the same serve without the variable (P003/P004). Its probe ran at 215 W (set outside the scripts); P004 measured
215 W at +1.8%, so power does not explain it. Stock re-applied 19:50:06 (receipts/p5/clock-state.txt).
Mechanism (engine c8b8993, common.cuh `ggml_cuda_q8_1_layout_host`): one-column decode takes SOA_ISUM unless the card is
Ampere (cc 800-889 -> planar PT, "+5.9% tg128 on a 3060") or BATCH_INVARIANT is set (-> PT with the warp-reduce
epilogue). Turing (cc 750) falls through to the Ada-tuned SOA_ISUM.

## Plan and gate

Hypothesis: "PT beats SOA_ISUM at one column on sm_75 by >10%." Arms: q8_0 N=16384 serve, stock slot 5 verified before
each load; BI unset / BI=1 / unset / BI=1 (alternating against heat drift); memclock_probe at 4k, 2 prompts x 400 x 2
reps. Gates written before the run (quoted):
- "confirmed if both BI=1 runs beat both unset runs and the mean gap is >10% (> 3x the P4 slot-1 drift of 1.4%);"
- "if confirmed, the engine fix is to extend the Ampere branch to Turing (cc >= TURING && cc < ADA), built for sm_75,
  then measured as a third arm (PT + four-accumulator epilogue, BI unset) with greedy identity vs a saved dump and
  tg128 in llama-bench; PR to the fork with the receipt."

## Method

p7_kernel_ab.sh: per arm stop, wait for idle VRAM (< 1,500 MiB), apply slot 5, refuse if power.limit is not 175 W,
serve, run memclock_probe (4k filler; code = ISO 8601 parser, prose = refrigerator; 400 tokens; 2 reps).

## Verdict

"CONFIRMED - planar PT beats the Ada SOA_ISUM kernel at one column on Turing by 12.3%." It also explains A-r3's 42.80:
PT via BATCH_INVARIANT, plus 215 W in its probe window. "BATCH_INVARIANT=1 is a no-rebuild workaround (PT + warp-reduce
epilogue) worth +12.3% on this card today."

## Toolbox

- Method: when an environment variable changes speed unexpectedly, read which kernel path it selects; an A/B of the
  variable alone (alternated) isolates a dispatch gate.
- Finding that transfers: kernel dispatch tables tuned for one architecture (Ada here) can leave older ones (Turing) on a
  slower path. Check the dispatch gate for your card's compute capability before tuning anything else.
- Model-specific: PTQ1_0 (ternary) mat-vec kernels; the one-column layout is the decode path.
