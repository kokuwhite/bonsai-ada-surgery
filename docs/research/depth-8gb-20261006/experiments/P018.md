## Question

Does the exact P013 request sequence (4k -> 16k -> 32k with "Say hi." between depths) reproduce the one-token stop, and
on which tail setting?

## Why

P017: the stop did not reproduce on a fresh 32k prompt; P013's 32k request had restored a 16k prefix from the RAM prompt
cache. P012 and P015 ran the same sequence without failing.

## Plan and gate

(quoted from the P017 result) "replay P13's exact quick_tps sequence (4k -> 16k -> 32k) x3 on the drafted default (tail
1, N=47360) and x3 on C2 tail 2; count one-token answers; capture texts and server logs. Any failure blocks the drafted
default until root-caused; zero in 6 replays -> recorded as unreproduced, kept under watch."

## Method

p18.sh alternates t1_r1, t2_r1, t1_r2, t2_r2, t1_r3, t2_r3; each is a fresh server and quick_tps at 4000, 16000, 32000
(3 prompts per depth = 9 answers per replay). One-token answers = lines with "(1 tok)".

## Toolbox

- Method: reproduce an intermittent failure with the exact request sequence (including warm-up requests that change the
  cache state), many replays, alternating arms, and count failures per arm.
- Lesson: an intermittent failure correlated with one setting (tail 2) can come from a shared component (the pool race)
  whose failure rate depends on timing and memory layout; keep a control that removes the shared component.
- Model-specific: hybrid models save and restore recurrent state with the prompt cache; restores of long prefixes are a
  correctness risk on any GDN/Mamba model.
