## Question

P022 saw long-mode 32k prefill of 300 (bin-p22) and 302 (bin-p12, P014c) vs 271 on bin-rc at the same N. Which build
step carries the +11%?

## Why

If a dev-build commit (#314 code, #209, pool log) speeds up prefill at depth, the release should carry it.

## Plan and gate

(quoted) "P23: long mode N=67840, prefill at 4k/32k on bin-turing (Turing fix only), bin-rc (+pool), bin-alpha PCT=0
(+#314 code, prefetch off, +#209), bin-alpha MAX_KB=1024, bin-rc again. Whichever step carries the +11% at 32k is
named."

## Method

run_arm.sh per arm with depths 4000 and 32000 (sequence 4k -> 32k; the 32k code prompt evaluates 28,512 tokens).
Order: turing_only 04:17:24, rc_turing_pool 04:20:51, alpha_pf0 04:24:14, alpha_pf1024 04:27:40, rc_turing_pool_r2
04:31:03.

## Results

| arm | server / free at load | prefill 4k | prefill 32k | decode 4k (mean) | decode 32k (mean) |
| --- | --- | --- | --- | --- | --- |
| bin-turing | 7,218 / 369 | 415.3 | 300.9 | 43.6 | 34.2 |
| bin-rc | 7,218 / 369 | 415.1 | 301.6 | 43.6 | 34.2 |
| bin-alpha PCT=0 | 7,216 / 371 | 417.1 | 302.1 | 43.7 | 34.1 |
| bin-alpha MAX_KB=1024 | 7,216 / 371 | 416.7 | 302.4 | 44.1 | 34.5 |
| bin-rc again | 7,218 / 369 | 413.7 | 301.4 | 43.6 | 34.0 |

"Identical within 0.5%: shared pool, #209 and #314 do not change prefill. P20's 271 came from its 4k -> 16k -> 32k
sequence: the 32k request evaluates only positions 16k-32k (all deep), P23's evaluates 4k-32k. sudo's floor used P20's
sequence, so the floor comparison stands: our incremental prefill at depth is -15% (32k) / -21% (60k, long mode) below
his."
"Cause (code + P16b): his fork converts q4_0 K/V to f16 per chunk and runs f16 MMA; ours dequantizes in the kernel. The
f16 route was avoided because its buffer is reserved at load for the full window (512 MiB at 131k)."

## Deviations, incidents, void runs

None.

## Verdict

"no hidden prefill gain - the 271 vs 301 was the request sequence."
P25 plan (in this entry): "f16 conversion for prefill-sized batches only (Q columns > 8), the buffer taken from the CUDA
pool at the actual KV length (128 MiB at 32k, 240 MiB at 60k) instead of reserved; decode keeps the in-place path. Env
switch GGML_CUDA_FA_PREFILL_F16=1, worktree off the release candidate. Gates: texts identical to in-place at 4k/32k;
prefill gain > 10% at 32k and 60k (P20 sequence) without a cliff at the long mode's N; decode unchanged."

## Corrections later

This entry corrects P014c's "-6% at 32k" and, in effect, P016b's "-3% at 60k" floor readings (both compared a different
request sequence with sudo's numbers).

## What it changed

The prefill gap against the floor was re-stated as -15% / -21% at depth, and the f16-prefill-from-pool idea (P025) was
planned.

## Toolbox

- Method: before hunting a "hidden gain" between builds, re-run all builds on the identical request sequence; check the
  evaluated token counts in each receipt.
- Finding: incremental prefill over a deep cached prefix (all new tokens deep) is slower per token than a prefill that
  starts shallow; report which one you measure.
- Transfers: any long-context benchmark that reuses the prompt cache.
