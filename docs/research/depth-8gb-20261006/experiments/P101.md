## Question

Do sparse host-tail reads (Quest-style page bounds, B cells per query) keep retrieval quality at real 8 GB depth
(245k, host tail ~200k cells, B = 8192 is ~4 %)? And what is the decode speed-up?

## Why

"Correction: sparse host-tail reads look viable (4070 measurement, a97f56a73)": on the 4070, B=8192 gave KL 0.0030 at
a 16k window, 12/12 needles and 10/10 exact copies at 160k. "Open: the budget at real depth (host tail 130-190k
cells on this card)." A coordination issue (#21) split the work: engine on the 4070, depth tests on the 2060.

## Plan and gate

Notebook: "bin-sparse = 87e2ac160 built for sm_75. Main 262k launcher; every arm: f16 mask, graphs off, chunked
prefill. Arms dense / B=8192 / B=16384 (pages 64, last 1024 always; FAST=1 decode-only; STAGE_MIN_Q=9 so unselected
pages are not read). At ~245k (host tail ~187k cells: B=8192 is ~4 %): 10 exact Python function copies
(code_needle, corpus = local stdlib pycode.raw) and 12 needle facts (needle_depth), separate prompts. Record
exact/correct counts and decode tok/s per code item. Gates for "sparse is safe at 8 GB depth": B arm = dense on
needles (12/12) and >= dense - 1 on code copies; decode speed-up reported. ~4-5 h (6 cold 245k prefills)."

## Method

- Six servers: (dense, s8192, s16384) x (code, needle). One cold ~241-244k prefill per server, then the items reuse
  the cached prefix.
- code_needle.py: ~245k tokens of Python source (pycode.raw); 10 short top-level functions (6-20 lines) at evenly
  spaced positions (0.074 to 0.945 of the prompt); "output the exact source of function F from file X"; exact match
  after stripping trailing spaces.
- needle_depth.py: filler with 12 facts ("The access code for vault N is NNNN") at evenly spaced positions; one
  question per fact; exact 4-digit match.
- Decode tok/s per code item from the server timings; summary mean over items 2-10.

## Results

| arm | code copies | needles | decode on code items (mean of 9, tok/s) | wall per item after the first (s) |

| dense | 10/10 | 12/12 | 7.38 | 26.8 |
| s8192 | 10/10 | 12/12 | 6.34 | 30.4 |
| s16384 | 10/10 | 12/12 | 6.34 | 30.5 |

Per code item, dense / s8192 decode (tok/s): _read_output 7.53 / 6.28; _divide_and_round 5.94 / 5.0; setcontext

evaluated tokens: 1,768.6 s (dense), 1,775.9 s (s8192), 1,778.8 s (s16384). Needle cold prefill (244,057 tokens):
1,775.5 s (dense).

## Deviations, incidents, void runs

- The plan expected a ~58k line and ~187k host cells. With the f16 mask (needed by the sparse prototype) the line was
  43,520 (44,544 in the dense code server), host tail ~201k cells at 245k, so B=8192 = ~4 %.
- The sparse INFO summary line is not visible at default server verbosity: every *.sparse_lines.txt is empty.
  "Engagement not confirmed by log; quality equal is consistent with either."
- The code items run lookup drafting (verify batches of 10-33 queries), outside the FAST path (<= 8 queries) of this
  build, "so the host tail is still read in full and the emulation adds its overhead."

## Verdict

Notebook (partial): "sparse B=8192 at 245k = dense on quality; no speed gain with lookup verifies ... s8192 ~10-15 %
SLOWER than dense (e.g. 5.0 vs 5.9, 8.7 vs 9.7 tok/s)".
Notebook (result): "245k, host tail ~201k: code copies dense 10/10, B=8192 10/10, B=16384 10/10; needles 12/12 in all
three. Decode on code items (lookup verifies): dense 7.38, s8192 6.34, s16384 6.34 tok/s (sparse -14 %: emulation
overhead, fast path not covering lookup verifies). Quality gate PASS at real depth; speed -> P102 (lookup off)."

## Corrections later

- #21 (4070, 23:49Z): "verify batches > 8 queries leave the fast path and run on the MMA kernel without tile skip ->
  full host read." Confirms the speed reading.
- P105 repeated the quality test with the d6c6e9f01 build: 160k 10/10 and 12/12; 245k 9/10 (sparse missed
  _calc_julian_from_U_or_W, which P101 got) and 12/12.

## What it changed

Quality at real 8 GB depth confirmed for the emulation build; docs/DEPTH.md quality row and docs/8GB.md "12/12 needle
facts and 10/10 exact code copies in one run". Speed work moved to P102.

## Toolbox (for the next model)

- Lever: Quest-style sparse reads of an offloaded KV tail (per-page K max/min bounds, keep the top pages per query
  plus a recent window and the whole VRAM part).
- Method: gate it on exact code copies and needle facts deep in the tail, with the dense run in the same layout.
- Model-specific: B=8192 cells with page 64 holds retrieval for this model at 245k.
- Transfers: the gate set; check that the fast path covers every decode op shape (MTP verify, lookup verify batches)
  before reading speed.
