## Question

Why did the no-head long mode at N=77,568 prefill at ~237 tok/s at 4k when C2 and B at N=38,656 prefilled ~400?

## Why

P012 anomaly: "prefill B 237 / 218 / 185 / 147 tok/s vs C2 405 / 341 / 264 / 177 at the same depths; B at N=38656 (P5)
prefilled 356-397 at 4k. Needs a controlled A/B (P14) before 77,568 ships anywhere."

## Plan and gate

P14 (quoted): "bin-p12, q4_0, no head, PCT=0, fresh 4k prefill (quick_tps depth 4000, first prompt evaluates 4,048
tokens): N=77568 BI unset / N=77568 BI=1 / N=38656 BI unset / N=77568 BI unset again. Reading decided now: if BI alone
restores ~400 tok/s -> the FA split under BI is faster for prefill on Turing (a finding); if N=38656 restores it -> large
N costs prefill (VRAM pressure on compute); if neither -> keep digging before 77,568 ships."

P14b (in the P14 result): "Two hypotheses: transient pool memory under pressure at 269 MiB free, or prefill attention
spanning all VRAM cells. P14b (during the sudo build, GPU idle, CPU loaded; fresh N=38656 control under the same load):
N=58112 (~570 MiB free) and N=77568 + GGML_CUDA_SHARED_POOL=1. Cliff near the margin -> pressure; gap proportional to N
-> span."

P14c (in the P14b result): "N=67840 ub 512 (~420 free), N=77568 ub 256 (half the prefill transients), controls N=77568
and N=58112 at ub 512; depths 4k and 32k. Pick the N/ub pair with the best prefill and decode at 32k and 64k for the
long-context mode. start-server-bin.ps1 gained BONSAI_UBATCH (copy only, shipped launcher untouched)."

## Method

quick_tps.py at the listed depths through run_arm.sh. The code prompt at 4k evaluates 4,048 fresh tokens (prefill
measure). P14c's 32k request follows the 4k request directly, so it evaluates 28,512 tokens (28,256 at ub 256).

## Deviations, incidents, void runs

- P14b: two arms were first refused: "not stock (215.00 W)" (REFUSED-ctl_n38656.txt, REFUSED-n58112.txt). "card read
  215 W after the apply - guard worked; run_arm now retries the apply until 175 W" (run_arm.sh: up to 4 tries, slot 3
  then slot 5, longer waits each try). Both arms re-ran and are valid.
- P14b ran under CPU load from the sudo build (by design; a fresh control under the same load was included).
- P14c ran after P017, not "after P15" as planned (P15 had run in between; order immaterial). The plan named depths 32k
  and 64k for the choice; the run measured 4k and 32k only.

## Verdict

The prefill drop at N=77,568 is a memory-pressure cliff near ~270 MiB free (transient prefill buffers growing in the pool
under pressure). It is not BATCH_INVARIANT and not attention over the whole VRAM line. It does not occur every load:
the same config at 214 MiB free had no cliff in P14c. ub 256 is not needed.

## Corrections later

- P14c's floor comparison ("-2.6% at 4k, -6% at 32k") compared unlike request sequences: P14c's 32k request evaluated
  28,512 tokens (4k -> 32k), sudo's 32k number came from a 16k -> 32k step (16,524 tokens). P023 (same day): "P20's 271
  came from its 4k -> 16k -> 32k sequence ... sudo's floor used P20's sequence, so the floor comparison stands: our
  incremental prefill at depth is -15% (32k) / -21% (60k, long mode) below his."
- P014c named "P19" as the next step: "make the reservation deterministic (reserve prefill scratch at load, e.g. a
  warm-up prefill or pool pre-grow at start) - candidate engine/launcher change." P019 was never planned or run (see
  P019.md). The long mode moved to smaller N with more free margin instead (P020 N=67,840; P027 N=53,248 with min free
  118 MiB during the 60k request).

## What it changed

- 77,568 did not ship; the long mode was re-sized (P020, P027).
- start-server-bin.ps1 (test copy) gained BONSAI_UBATCH; ub 1024 later became part of the long mode (P026/P027).
- run_arm.sh gained the stock-apply retry (used by every later arm).

## Toolbox

- Method: bracket a speed cliff with N values at different free margins and one "span" arm (here N vs free VRAM); a cliff
  near a margin means memory pressure, a gap proportional to N means work that scales with N.
- Finding that transfers: on WDDM with ~200-300 MiB free, transient prefill buffers can push the process into a slow
  state for a whole load; whether it happens depends on load-time state. Keep prefill headroom (here >= ~400 MiB at
  load worked) or reserve scratch at load.
- Lesson: compare prefill only on the same request sequence (the evaluated token count is in quick_tps output).
