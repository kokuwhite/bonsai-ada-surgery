## Question

Which real kernels launch per decode graph, by name? This is the fusion target list ("op-timer counts include no-op
nodes and overstate launches").

## Why

P37c: small ops are ~2.8 ms/token. A list of real kernel launches tells which fusions remove launches.

## Plan and gate (as frozen before the result)

"Before it [P40]: P41 kernel census (dev build, GGML_CUDA_GRAPH_STATS=1, plain model, one decode request): real
kernels per decode graph by name - the fusion target list (op-timer counts include no-op nodes and overstate
launches)." P41b: "census with LLAMA_ARG_LOG_VERBOSITY=5 (ggml INFO lines are filtered without it - the first census
was empty)." No gate (reading).

## Method

Start the raw server with the stats switch, send one short greedy completion, grep the server's stderr for
"cuda graph stats" and keep the following lines.

## Corrections later

- P55b (2026-10-09) found that graph #1 is the warm-up graph (`llama_decode({bos, eos})`, 2 tokens), not the decode
  graph; the decode graph is #2. In the plain decode graph (#2) the add kernel count is 48, not 128. So the P48 premise
  ("128 residual adds per decode step") read the warm-up graph. In the drafting mode's verify graph (2 columns, P55b
  census_mtp graph #2) there are 128 add kernels, so the count is right for the served drafting step, not for plain
  decode.
- P55b also confirmed: "all PTQ1_0 mat-vecs 1-column" in decode; gate+up fused in only 40 of 64 FFN layers -> P76.

## Toolbox (for the next model)

- Method: count real kernel launches per CUDA graph with a stats switch; set log verbosity high enough that INFO
  lines are kept.
- Transfers: the first graph a server builds can be a warm-up graph with a different batch size. Identify the graph
  that is reused during decode (here "CUDA Graph id 66 reused") before you read counts from it.
