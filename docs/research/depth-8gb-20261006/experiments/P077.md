## Question

Without the staging buffer (attention reads the host part in place), does the 262k window cost no VRAM cells, and is
decode / prefill acceptable?

## Why

P75: the launcher reserves the tier staging buffer, (ctx - N) x CellBytes / 16, so the VRAM line falls 8,738 positions
per extra 131k of window.

## Plan and gate

Notebook: "P77 (plan, after P75): GGML_CUDA_KV_TIER_STAGING=0 (attention reads the host part directly, no staging
buffer); with no staging, N = 47,040 + 8,192 = ~55,232 at any window (use 54,784 for margin). Arms, drafting preset,
bin-0046, quick_tps 4k/32k/64k/96k/128k: A 131k preset; B 131k staging 0 N=54,784; C 262k staging 0 N=54,784.
Gates for "262k default": C decode at 32k/64k/96k >= A (or within 2 %), 4k within 2 %, min free >= 60 MiB, 0 one-token,
prefill at 64k/128k not worse than P75 by > 10 %. B vs A isolates staging-vs-direct cost at the same window."
Amendment before the run: "each arm now has a 10 s VRAM trace (<arm>.mem.txt, "trace min free" line, wrap corrected).
Arm A (131k preset, the shipped default) gets the same check, so it also shows if 131k goes below zero at 128k depth."

## Method

Arms A, B, C in order, one server each, quick_tps at 4000, 32000, 64000, 96000, 128000 (extending), free VRAM every
10 s (values above 4,000,000 have 4,194,304 subtracted).

Notebook reading:
"1. With staging off, the window size costs nothing (C = B).
2. Decode +26 % at 64k, +15 % at 96k, 0 % at 128k: mostly the extra 4,608 VRAM positions (host rows at 64k 14k -> 9k);
staging vs direct read for decode at equal N is not isolated.
3. Prefill past the f16-prefill limit (32,768 cells with drafting) reads host rows in place once per query tile:
96k -60 %, 128k -70 %. Not acceptable as a default (each agent turn at 96k: ~10 s prefill, not ~4 s).
4. C load free is 128 MiB less than B: the f16 KQ mask is n_ctx x ubatch x 2 B (128 MiB more at 262k). The launcher
FixedMiB does not scale it with the window -> the P75 and C over-commit. Launcher bug (12 GB cards at 262k too)."

## Deviations, incidents, void runs

- C went below zero free VRAM from the first request (load free 185 vs B 313).
- P80 (queued as 46, tail 2 at 200k with staging off, N 54,784) started after this run on the same over-committed
  setting and was stopped after 2 minutes (see P080).

## Verdict

Notebook: "Gates for "262k default": decode pass, 4k pass, min free FAIL, prefill FAIL. Not adopted."

## Corrections later

- P81: "F = A: on Turing, staging vs in-place read does not change decode at equal N. The decode gain in P77 was all
  N." (Reading 2 was right to say it was not isolated.)
- The mask cost found in reading 4 led to P81's mask-aware launcher and P82's packed mask.

## What it changed

Not adopted. Two levers found: partial staging (keep fast prefill to a depth, read in place past it) and the KQ mask
size.

## Toolbox

- Lever: tier staging buffer. It makes deep prefill fast (host rows copied to VRAM once per op, f16 path) but costs
  VRAM that grows with the window. Without it, prefill past the f16 limit reads host rows once per query tile: 2-3x
  slower at 96k-128k.
- Hidden VRAM item: the f16 KQ mask = n_ctx x ubatch x 2 B (131k x 512 x 2 = 128 MiB; 256 MiB at 262k).
- Transfers to any llama.cpp KV-offload scheme: count the mask and staging per window, and trace VRAM through a deep
  prefill.
