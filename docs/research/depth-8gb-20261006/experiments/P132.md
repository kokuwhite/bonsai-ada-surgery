## Question

With sparse on, does q3_0 K/V still beat q4_0 at 160k and 245k, and do both stay inside VRAM?

## Why

The 4070's Q06 request: "Then the same with sparse on (the #49 launcher): the decode at 160k / 245k, with q3_0 and
with q4_0." With sparse, q3_0 also cuts the staging bytes and the host-tail reads (the P114 post on #21).

## Plan and gate

Script header: "P132 (#21, Q06): sparse ON (launcher-sparse defaults, int8 bounds) with q3_0 vs q4_0 K/V on
q3-on-sparse 4dbfe57d4 (bin-q3sparse), 160k -> 245k, one server each, 10 s trace. Gates (declared here, before the
run): q3_0 decode >= q4_0 at 160k and 245k (report the ratio); 0 one-token; trace min free >= 60 MiB in both arms;
post both VRAM line summary lines."

## Method

(Planned.) Two arms, one server each, quick_tps 160000 then 245000; 10 s trace; kv and "VRAM line" launcher lines;
sparse_mask count.

## Results

Not run yet.

## Deviations, incidents, void runs

- The P114 post on #21 says "With sparse, q3_0 also cuts the page-bound and staging bytes". The page-bound layout the
  4070 posted on #49 (16 x 4 x (2 x 256 + 2) / 64 = 514 B per host cell) and the launcher formula in 8a47ffe have no
  KV-type term, so q3_0 should not change the bounds reserve; it cuts the KV cells and the staging bytes (CellBytes /
  16 per host cell). P132's "VRAM line" lines will show it.
