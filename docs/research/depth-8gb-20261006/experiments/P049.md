## Question

Main turns lookup drafting (ngram-mod before the MTP head, lookup limit 32) on by default but off on 8 GB: "the 8 GB
margin is not measured for it". Is it a win on 8 GB, with the same text and no memory trouble?

## Why

"Mechanism: the recurrent rollback ring stays sized for MTP (draft 1 here); a longer lookup draft takes the server's
checkpoint path, so no extra 150 MiB planes. Risk: the 33-column verify batch's compute buffers against the 225 MiB
margin."

## Plan and gate (as frozen before the result)

"Arms: BONSAI_LOOKUP=0 / =1, bench/lookup_ab.py (quote, edit, plain) at depth 0 and 64000; then lookup=1 at 0 again.
Gates: quote and edit faster with lookup at both depths; plain within 2 %; same text hashes as lookup=0 (rounding-level
MTP differences allowed and listed); no server death, no prefill cliff, min free VRAM >= 80 MiB. Pass -> PR to main:
the 8 GB preset turns lookup on (with this receipt)."

## Method

lookup_ab.py, thinking off, greedy: quote = 4 CPython stdlib files (~150 lines each: textwrap.py, shlex.py,
fnmatch.py, csv.py), "output the complete file again with one comment line added"; edit = the same files, one edit tool
call whose oldText quotes lines of the file; plain = the 3 quick_tps prompts (code, prose, bash, 400 tokens). Per
request: decode tok/s, tokens, drafts proposed / accepted, sha256 of text (first 12 hex), wall time. Free VRAM sampled
every 2 s. At depth 64000 a filler preamble of ~64k tokens is put in front of every request.

## Deviations, incidents, void runs

1. P49 64k arms and the first P50 failed at once: "lookup_ab.py imports quick_tps from its own folder (fixed: bench
   path)" (receipts/p49/{mtp,look}_d64k.out.txt: ModuleNotFoundError).
2. Edit hashes differed in every arm, also between the two lookup runs: "lookup_ab.py hashes the tool_calls with the
   server-generated call id - a bench bug (fixed in my copy: name + arguments only; upstream the fix to main)". The fix
   went into PR #9.
3. The overnight GPU was idle 01:44 -> 07:20 (cron did not fire; events file). P49b ran in the morning (jobrun8).

## Verdict

P49 (depth 0): quote x2.17, edit +5 %, plain within 0.4 %, min free 249 MiB, alive. P49b: all gates pass - quote and
edit faster at both depths, plain within 2 % (-0.3 % at 64k), 21/22 same text (one rounding-level difference at 64k),
no death, min free 82 MiB (gate >= 80: a narrow pass). Cary: "known win, ship it" -> PR #9.

## Corrections later

- The shlex.py 64k quote variant 137637.. is "a known 64k variant" (P79, fillers 2026-10-09).
- P53: HumanEval with lookup on = 158/164 (quality holds). P57: 89-min soak at 64k passed. P50: the deep end (120k).
- The P49 runs had the shared CUDA pool on (preset at that time); P64/P69 later found the pool causes 1-token answers
  on fresh long prompts. No 1-token answer appears in P49/P49b.

## Toolbox (for the next model)

- Lever: n-gram lookup drafting from the context in front of the MTP head. Huge gain when the answer quotes the prompt
  (file rewrites x2.1-2.2), small on edits (+5-16 %), none on free text.
- Model-specific: costs 768 positions in VRAM on this card (54,784 -> 54,016) for the 33-column verify buffers.
- Transfers: a bench that hashes tool calls must drop server-generated ids. Test the mechanism at depth too (64k), not
  only at depth 0; a filler-prefixed prompt re-prefills ~64k tokens per request when the prompt changes inside one
  message (P59).
